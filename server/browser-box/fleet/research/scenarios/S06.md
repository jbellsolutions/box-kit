# S06: a platform UI change breaks a released procedure

Role: scenario stress-tester, group 2. Paper walk of the drafted design; nothing is built. DECISIONS.md and the
verification reports win over dossiers.

**Verdict: handled-with-gaps.** The first half is well designed: an L1 replay re-verifies the target's role and accessible name, a mismatch
is a miss and never a click, `selfHeal` stays off, a miss climbs the ladder, a repaired step is only a *candidate*, and the
agent is told not to imitate a quarantined procedure (verification IDs SH-1, SH-2, SH-8 in
`research/verification/stagehand.md`; MS G3.3). I checked whether any CH or DEC sentence is *literally* contradicted and found none:
gate G is deterministic policy, and D5 itself authorises the climb ("Every browser step climbs this ladder"; "A rung that succeeds on a new
page becomes a candidate L1 step"). The defects are in what D5 and D13 leave out. The second half of the scenario (quarantine, release after
accepted outcomes, rollback) cannot be run as written, and the climb is unsafe for the one kind of step that matters:

1. For an **irreversible step** D5 lets a model pick the control after an L1 miss, with no deterministic constraint on *which control*.
   The first use of a repaired target is therefore a live, irreversible click on a client's account, before any candidate review or
   canary. Gate G checks scope, authority, content hash and account header, not the control. This is a **DECISIONS defect (D5)**, not
   an ARCH slip (S06-1).
2. The **read-back verifier is a UI too.** The same change that breaks the click can break the receipt reader, turning every
   success into `uncertain` and, if a "safe after negative read-back" pair is ever enabled, into a retry (S06-2).
3. **Quarantine has no automatic trigger**, **release has no owner for non-effect steps and none across tenants** (pending N-5), and
   **rollback restores the old-UI steps** (S06-3, S06-4).

## The scenario, pinned down

Procedure `facebook.group_post@3` (digest `a1b2c3d4`), `kind: browser`, **released**. Steps (ARCH §3.7 shape):

| Step | `op` | `effect` | `rung_hint` | `l1_cacheable` | `expects` / `readback` |
|---|---|---|---|---|---|
| S1 | navigate to the group URL | none | L0 | no | URL prefix |
| S2 | click "open composer" | none | L1 | yes | composer textbox present |
| S3 | focus the textbox | none | L1 | yes | textbox focused |
| S4 | fill the approved text verbatim | none (reversible) | L0 | no | `innerText` equals content |
| S5 | pre-submit check | none | L0 | no | text hash and account header |
| S6 | click "Post" | **irreversible** | L1 | yes | composer closed |
| S7 | read-back in the feed | none | L0 | no | `dom_readback`: hash or text prefix |

Used by identities in several tenants. Under **Answer A** (API-first, recommended) this is the narrow no-API set: a handful of
identities, per-action approval, client risk acceptance. Under **Answer B** (browser-first) it is most of the fleet. The blast
radius below scales with that answer (ARCH §8). Assumptions (mine): `browser_hitl: per_action`, `agent_clicks`; Q-07 default
(no logged-in page to a System 1 vendor until cleared; no DM to any model; S1 §3.6 rule 5); the L1 cache is per tenant (ARCH §3.9).

The platform ships a new composer to a share of accounts first. Variants therefore coexist for a while.

## Walkthrough

### 0. Before the change

- `procedures` row: `release_state: released`, `accepted_outcomes ≥ 3`, `digest a1b2c3d4`, `previous_digest` set (ARCH §3.7).
- `l1_entries` for S2, S3, S6, one per `(platform, procedure_digest, step_key, url_pattern, dom_fingerprint)` per tenant, state
  `released`, with `target_fingerprint {role, accessible-name pattern, frame path, nearby-text hash}`, `hits`, `misses`,
  `last_verified_at` (ARCH §3.9). **`dom_fingerprint` is never defined** (grep: ARCH §3.9, DEC D5, MS §4.5, SH §9.3 name it;
  none says what is hashed or how tolerant it is).
- A normal run: S1 L0, S2 L1, S3 L1, S4 L0, S5 L0, S6 L1, S7 L0. Seven of seven executor commands at L0/L1, no model call.
  System-1 share for the procedure = 100% on this run (S1 §6.1 counts L0, L1, L2; it is not evidence the deciders work).

### 1. The first run on a changed account (identity A)

Scheduler (C5) or the Hermes `publish` path runs the procedure (ARCH §4.2). Preflight authority passes (approval `ap_12`, hash
match). Wake, probe `ok`. Executor (N3) runs the steps with fencing token T.

**S2, open composer.**

1. L0: the procedure locator (role `button`, name "Write something...") finds nothing: the control is now a differently named
   button inside a different container. Miss.
2. L1: the lookup key includes `dom_fingerprint`. Two cases, undefined in the design:
   - the fingerprint changed (a coarse page-skeleton hash): **no L1 row is found at all**. No `miss` is counted against the
     released entry; nothing signals "this entry is stale"; the entry keeps serving other accounts still on the old UI;
   - the fingerprint is coarse enough to survive: the row is found, the executor re-snapshots (0 model calls, 0.2-1.3 s,
     SH §5.2), finds the stored xpath in `xpathMap`, reads that line's role and name, compares to the stored fingerprint.
     Mismatch: **a miss, never a click**; `misses + 1` ("a miss counts against the entry", ARCH §4.3). With `selfHeal:false`,
     a stale xpath fails in about 16 ms with 0 model calls (SH §14 F8; Stagehand act docs, `act(Action)` replay).
   Which of the two happens decides whether the fleet ever learns about the change from L1 counters (S06-5).
3. L2: build up to 180 candidates from a fresh `page.snapshot()`, one `/decide` request (`target`, `blocker`, `done`, `risk`).
   **Under the Q-07 default this rung is closed on a logged-in page**: `account_page` calls to a System 1 vendor are refused until a
   (provider, host) pair is cleared; "logged-in steps then use L0, L1, the reasoning model or a human" (S1 §3.6 rule 5). On a DM
   surface even the reasoning model is off (SH §6.2 item 13). So in the default configuration the climb is **L1 miss -> L3**.
   (If cleared: the decider returns a choice with confidence; the threshold row was calibrated on the old UI. Nothing re-calibrates on
   a UI shift; "confidence is not portable" is about providers, but it is also not portable across page versions.)
4. L3: Stagehand `observe` through the shim (GLM 5.3 Flash, `reasoning.effort=low`, the page text goes to an allowlisted OpenRouter
   provider). The returned `Action` passes the sanity checks (lowercase mouse button only), then `act(Action)`.
   Cost about $0.00013 per `observe` on an easy page, about $0.001 on a dense one (SH §5.1); p50 about 1.7 s, 7-8% defective or
   runaway acts on dense pages (34-52 s each at an 8K cap; CONSISTENCY C-22).
5. Post-condition: `expects` (composer textbox present) in code first; if the new composer's landmark differs, `expects` itself fails
   and the step fails after the click was made. The ladder then climbs again from a page the click already changed.
6. Success writes a **candidate** L1 entry (state `candidate`, `origin {rung L3, model, provider}`). It is not served until released.
   The run continues.

**S3.** Same, if the textbox's accessible name changed.

**S6, click Post (irreversible).** This is the step that matters.

1. L0 locator and L1 entry both miss (same reason).
2. L2 (if cleared) or L3 chooses a control. The procedure step has no `target_rule`; ARCH §3.7 `steps[]` is
   `{key, op, rung_hint, effect, effect_kind?, l1_cacheable, expects, readback?}`. The L2 candidate list is "up to 180
   candidates" from the whole snapshot (ARCH §4.3), not pre-filtered to controls whose role and name match the step.
3. Gate G (ARCH §4.3, applies to "every rung"): classify (declared `effect: irreversible`), scope `publish` OK, authority `ap_12`
   subject hash OK, governor reserve OK, **content check** (composer DOM text equals approved hash; account header equals
   handle) OK, intent row committed (`effects.state = intent`), then act.
   - What gate G does **not** check: that the element clicked is the submit control. A new design commonly adds adjacent controls
     (hypothetical illustration, not sourced: "Post", "Schedule", "Boost", "Share to another surface"). The decider or GLM picks
     among them by probability. CH invariant 7 says irreversible actions are "gated by deterministic policy ... never by a model
     probability"; here a model probability decides *which* irreversible thing happens, and the policy checks the content, not the
     control. The approval subject names "audience, irreversible effects" (ARCH §3.7), but the pre-submit check (ARCH §4.7 step 5)
     reads back text and account header only, not audience, visibility or attachments, which a redesign can also change.
   - The canary rule (MS S2, CH invariant 5, O-13) covers "a new identity, a new persona, a new pin or a new procedure". A changed
     UI under an unchanged digest is none of those. D5: "A rung that succeeds on a new page becomes a candidate L1 step, released by
     D13's rules"; but the L3 success **already acted on the client's account in this run**. The candidate is reviewed after the
     fact. The first live use of the repaired target is the production click.
4. `expects` (composer closed) passes or fails. If it fails after the click, the ladder climbs again; a second attempt reaches the
   `intent` row and returns `outcome_uncertain` (ARCH §3.6 protocol): the identity is held. That is the protection working, and the
   cost: a UI change can put identities into `hold(uncertain_effect)` en masse, each needing a human reconcile.

**S7, read-back.** `dom_readback`: navigate to the group feed, match hash or text prefix inside the grace window. A redesign changes
the feed markup too; the reader may stop finding posts that are there. Result: `uncertain` + hold for every effect, because the
negative read-back is a hypothesis for browser social actions (DEC D13; CH invariant 5). With a "safe after negative read-back" pair
enabled (`effects.retry_allowed`), the same failure becomes `reconciled_absent`, which "may be retried" (ARCH §3.6): a duplicate
post per affected account. Defaults keep every pair unsafe, so by default it is a reconcile storm, not a duplicate storm
(S06-2). CH "What nobody does, ever" also lists "Retry an effect whose outcome is uncertain", which ARCH §3.6 and CH invariant 5
leave a loophole in.

### 2. Detection: how the fleet learns it was a UI change

What is written:

- Per step `run_steps.rung` and `decided_by` (ARCH §3.9); metrics C17 "System-1 share per procedure"; SH §12 "L1 mismatch rate".
- `feedback(kind:"site_changed")` from a Hermes profile: "quarantines the affected L1 entries and, on repeats, the procedure"
  (ARCH §5.3 tool 14). The `fleet-stagehand` skill tells the agent: "The same step failing twice on a flow that used to work: stop.
  `feedback` with `kind: "site_changed"`".

What is **not** written: any threshold ("repeats" is not a number), any aggregation across identities, any alert. The M5 alert list
(MS §4.7 Observability; G5.9) names checkpoints, uncertain effects past grace, proxy/fingerprint drift, failed bundle upload, node
out of slots, disk. Not L1 mismatch rate, not a drop in System-1 share, not a spike in L3 spend, not a surge of `uncertain` effects
on one procedure. And a report from one token can quarantine a procedure that every tenant shares: a confused or prompt-injected
profile, or a tenant on a staged-rollout variant, takes everyone's procedure out (S06-3).

Meanwhile every identity that runs the procedure repeats the S2/S3/S6 climb on its own schedule, each paying L3 and each risking the
irreversible mis-click in S6.

### 3. Quarantine

With a `site_changed` report: the affected L1 entries are quarantined; on repeats the procedure goes `quarantined` and the registry
answers `not_released` (ARCH §5.5). Consequences:

- Hermes: `not_released` -> "do not imitate the procedure with `act` or `task`; ask for its release with `feedback`" (fleet-router,
  AGENTS.md). Correct and safe.
- Scheduler: manifest items run "without a Hermes call" (ARCH §4.11). Each due item now fails validation with `not_released`. The
  notifier list (ARCH C16) covers `needs_reauth`, `checkpoint`, `needs_approval`, `uncertain` past grace, drift, upload failure,
  budget caps. Not "procedure quarantined" or "scheduled item skipped". Scheduled client posts silently do not go out (S06-10).
- Vocabulary: ARCH `l1_entries.state` is `candidate|released|retired` (§3.9); SH §9.3's entry sketch is
  `candidate|released|quarantined` with counters `replays, verified, mismatches, outcome_failures`; `feedback` returns
  `step_quarantined`. There is no `quarantined` state for an L1 entry in ARCH (S06-6).

### 4. Repair and release

What the design says: candidates are produced by the ladder (S2, S3, S6 above) and by `task`/`feedback proposal`; "Released by D13's
rule: three distinct owner-accepted outcomes. Rollback is per procedure; the owner decides" (SH §17.3, ARCH §3.7). Walk:

1. **Whose outcomes?** `accepted_outcomes` is a field of the *procedure*. For an L1 entry there is no counter of accepted outcomes.
   MS M0b item 6 asks to "define 'owner' for a multi-client fleet" and N-5 leaves it undefined. The verifier for a human-accepted
   outcome is `owner_review` (ARCH §3.7), which CH invariant 5 itself says "does not scale to unattended posting".
2. **For non-effect steps (S2, S3) there is no outcome to accept.** An owner cannot judge "click on composer button". The only checks
   are code (`expects`) and the next step working.
3. **Per-tenant scope.** The L1 cache is per tenant by default (ARCH §3.9). Every tenant re-discovers the same UI change, produces its
   own candidates, and needs its own three accepted outcomes. A shared tier is "a later review". Tenants on the old variant keep the
   old entries; tenants on the new variant re-learn.
4. **Canary.** MS S2 and O-13 say a new procedure runs read-only first, then low-volume own-account effects. That needs an owner-owned
   logged-in account on the platform, in a group, on the *same UI variant*. CH forbids fake accounts; MS N-1 allows Justin's own
   accounts only for M6a. Staged rollouts mean his account may not see the new UI. If there is none, the "release after accepted
   outcomes" happens on clients.
5. **Cost while waiting.** Until a candidate is released it is not served (SH §9.3: "the old entry keeps serving until the candidate is
   released"), so every run on the new variant takes L3 for S2, S3, S6 (default Q-07: L1 -> L3). Illustration: three of seven
   commands at L3 gives a System-1 share of 4/7 = 57% for the procedure instead of 100%; model cost per run about 3 to 6 calls at
   $0.001-$0.002 = $0.003-$0.012 (`estimate`; dense-page list price). Latency adds 3 × 1.7 s p50 with a heavy tail. The money is small.
   The share drops, and each L3 pick on S6 carries the S06-1 risk.

### 5. Rollback

`procedures.previous_digest` is "a rollback pointer; rollback is per procedure" (ARCH §3.7). In this scenario it restores the steps
and `expects` written for the **old** UI. They are the ones that broke. Rolling back after a bad *new revision* is meaningful; rolling
back because the *platform* changed is not. For L1 entries (key `procedure_digest or null`) rollback is undefined: do entries built
under the failed digest become `retired`? Do old-digest entries resume serving? (S06-4.) Variants complicate it: because
`dom_fingerprint` is in the key, old-UI and new-UI entries can coexist, so rolling back a digest can strand the new-variant accounts.

### 6. What the humans and Hermes see

- Hermes profile: a run result whose `steps[].rung` shows L3 on a flow that used to be L1; maybe `outcome_uncertain`; later
  `not_released`. The skill says "if a known flow starts doing that, the page may have changed".
- Owner: approvals as usual until quarantine; then possibly nothing (no notifier row), then an operator-console item (the
  console's screens are unspecified, ARCH C1). The first signal may be a client asking why the Tuesday post did not appear.
- Vault: Run notes with `uncertain` and L3 rungs; the daily note's **Held** list.

### 7. What is handled well (credit)

- Positional-xpath hazard is understood and tested by design: re-verify role and name; mismatch is a miss; `selfHeal:false`; Browser-Use
  stale index checked too (ARCH §4.3; MS G3.3 mutation suite; verification SH-2 and SH-8 and its missed issue 2, `research/verification/stagehand.md`).
  There is no vendor cache to fall back on: v4's cache reports `DISABLED` on Steel (SH-1), so the fleet's L1 is the only replay.
- Reads (`extract`, notification checks, profile reads) are never cached or replayed (SH §9.3).
- A heal is a new candidate, not an in-place rewrite; real rung, model and provider are recorded on every entry.
- `ModelCallForbidden` on L1/L2 steps makes "zero generative calls" a production invariant (SH §6.3).
- The intent row before the click and `outcome_uncertain` on a repeat stop the worst double-effect cascade by default.
- Agents are told not to imitate a quarantined procedure with `act` or `task`.
