# S02. A 30-identity social campaign for one client

Stress test, group 1. Read against the design as written on 2026-10-10. **Nothing described here is built.**
No developer app has been applied for, no connector exists, no platform approval is recorded.

**Verdict: handled with gaps.** The publish path is sound on paper: an approved manifest, a governor, an intent
row before the call, an API read-back as the receipt (ARCH §4.6). The gaps are around it. There is no way for the
writing agent to get a manifest or media into the fleet (S02-1, S02-2). One approval per account and platform
multiplies the human work (S02-3). The "first post needs a human" gate is in the milestones but not in the gate
that runs (S02-4). The duplicate-content rule is written three different ways. The "cross-client" wording would let
one client's 30 accounts carry the same words, and no wording defines the test (S02-5). The verdict would turn
into "breaks" if the check is cross-client only and the manifest carries the same text for every account.

## What the walk assumes

- One client, "Acme", a multi-location brand. **30 identities** = 30 brand accounts. Each may hold up to five
  platform accounts: a Facebook Page, an Instagram professional account, TikTok, X, a LinkedIn Page. This is the
  only reading that makes both "30 identities" and "five platforms" true (ARCH §3.3 `identity_platforms`).
- Everything is on the **API channel**. No browser is woken. The client connects each account by OAuth in
  their own browser, not through the viewer (ID §2.2, SC §2.1).
- One Hermes profile holds one token. A token carries one `tenant_id` (ARCH §3.4), so one profile per client
  falls out of the design. The token is bound to the 30 identities with scopes `read`, `draft`, `publish`.
- Workload for the arithmetic: one post per identity per platform per day. **This is an assumption, not a
  forecast.**
- Defaults hold: Q-01 API-first; Q-05 treat the X "Automated" label as required, so no X publishing for client
  brand accounts; Q-06 nothing applied for, every cap $0.

## Gaps

Severity: blocker = cannot finish safely as designed. major = can finish only by guessing or at a real risk.
minor = a missing detail or ownership.

| ID | Severity | Target doc | Problem | Proposed fix |
|---|---|---|---|---|
| S02-1 | major | architecture | **No way to author, list, revise or revoke a manifest.** The 14 tools (ARCH §5.3) have none. `publish` takes a `manifest_item_id` that a person must hand over (FS §1 step 3). The data model has `approvals.kind = manifest` but no tool creates one. HR gap 6 notes that nothing lists items. So the agent that writes the words (the SOUL division of labour) cannot hand them to the thing that publishes them. | Add a write tool `manifest` (scope `draft`): propose, revise, list, get, with a diff between revisions. Approval and revocation stay with operators. List items in `identity_status.next_scheduled`. |
| S02-2 | major | architecture | **No media path.** Manifest media is `{ref, sha256}`, but nothing defines `ref`, and no tool uploads. Instagram wants JPEG on a public URL; TikTok wants a verified domain (SC §3.1.2, §3.2). Media hosting is in MS §4.6.3 and SC §2.1 but is not among ARCH components C1 to C17. Converting a PNG to JPEG changes the sha256, so the approved hash would not match the published file. A public URL made early can leak unreleased assets; it must also outlive the publish (video processing polls). | Add a media store: ingest, convert and hash **before** approval so the approved hash is of the artifact that is published; check platform specs at approval time; serve each file from the verified domain on an unguessable, short-lived URL. |
| S02-3 | major | architecture | **One approval per account and platform.** Manifests are keyed by identity and platform (ARCH §3.7). The campaign needs 30 to 150 approvals, and an edit to any item makes a new revision that needs approving again. There is no campaign object, no batch approval, no cross-platform status. The approver is an operator; the client's own sign-off on content is not modelled (N-5 leaves "owner" undefined for a multi-client fleet). | Add `campaigns` that group manifests. One approval event covers a named set, with a per-manifest diff view. Add a tenant-scoped client approver role (see S01-3). Show campaign status per platform. |
| S02-4 | major | architecture | **The first-post gate is not in the gate that runs.** MS §4.6.1 and SC §7 say the first post per account, per new content type and per new destination always needs a human. FS tells the agent to expect it. Gate G (ARCH §4.3) has no such step, and §4.11 says manifest items run without a Hermes call. There is no table that remembers which account has posted what. Launch day is exactly when 30 accounts all have a "first". | Add `account_firsts` and a gate G step. Decide whether the manifest approval may satisfy it (only with an explicit per-account tick) or an extra approval is required. Say so in §4.11. |
| S02-5 | major | charter-soul | **The duplicate-content rule is written three ways.** CH invariant 8 and the red line: "across client accounts". MS §4.6.1 and SC §2.1: "cross-client". ID §6 row 12: "across all client accounts". X's rule covers "one account or over multiple accounts you operate" (SPV V-7), which includes one client's 30 accounts and one account's own history. "Substantially similar" has no test. There is no error code for it in ARCH §5.5. Under the "cross-client" wording, identical copy can go to Acme's 30 accounts. Under the stricter wordings it means 30 different drafts per slot, which the plan never prices. | State the scope: same account, same client, all clients. Define the test (normalised text plus media hash first; a similarity threshold to measure). Add the error code `duplicate_content`. Make the check run at approval time as well as at publish time. Tell FS to write per-account variants. |
| S02-6 | major | architecture | **API-only accounts must carry an IP.** ARCH §3.2: `proxy_id` is mandatory and unique, so 30 API-only identities buy 30 static IPs they never use (about $2.5 to $3.3 each per month, `vendor-claim`; ID §3.2). ID §2.1 step 0 and §9 item 1 recommend a row with no IP, and say to add a browser identity later "as a new record linked by client and handle". But ARCH §3.3 makes `(platform, handle)` unique across the fleet, so the later record collides. | Split `platform_accounts` (unique per platform and handle; owns the API connection) from `identities` (the browser self; `proxy_id` required there only). An account may have zero or one browser identity. |
| S02-7 | major | architecture | **No record of app approval, and no rule for items on a blocked platform.** G4A.5 needs a state per platform; ARCH has no table. A manifest can be approved for TikTok while TikTok is `unavailable`. What happens to those items is unspecified: they become jobs, fail `channel_unavailable`, and their window passes. The notifier list (ARCH §2.1 C16) has no "item missed" event. | Add `platform_apps` (platform, app, state, access level, dated source). Preflight at approval: refuse or mark each item `blocked_until_ready`. When a window closes undelivered, mark the item `missed` and notify. |
| S02-8 | major | architecture | **The governor misses dimensions this campaign hits.** Windows are per account, app, provider and identity-day (ARCH §2.1 C11). Missing: a per-member window (LinkedIn's 100 per member per day follows whoever authorised, inference); tenant fairness on a pooled app (LinkedIn's 500 per app per day serves every client, and one developer app per platform is a rule, SC §2.1); reads that spend the same budget (read-back, `content_publishing_limit`, token health). For Meta, TikTok and LinkedIn the design names no live source for limits (only X headers and the Instagram limit endpoint). | Add the dimensions: grantor, tenant share of an app, and read classes with priority (effect, read-back, health, analytics). Name each platform's live source, or mark the cap static and "to verify". Re-read caps at build time (SC §4). |
| S02-9 | major | architecture | **The API-channel plumbing is not in the architecture.** Absent from ARCH's components and tables: OAuth start and callback, per-platform scope selection, the consent ledger (X needs express consent per automated action type), the token refresh scheduler (Instagram 60 days, TikTok one day access and 365 days refresh), revocation handling, opt-out ledger. MS §4.6.1 and SC §2.1 require all of them. Also ambiguous: ARCH §4.6 step 1 maps a 401 to `needs_reauth` with `kind:"api_connection"`. If that sets the identity-wide state (§3.8), one expired TikTok token stops Facebook posting. | Add a connector-support section and tables (`consents`, `opt_outs`, `connection_health`). Connection health is per identity and platform and **never** sets `identities.state`. |
| S02-10 | minor | architecture | **"Match the content hash or a marker" is not a method.** Platforms rewrite text (link shortening, previews, caption handling; inference, not researched). A strict hash gives false negatives, which become `uncertain` and a hold on the whole identity (see S03-9). | The receipt is the id the write returned plus a fetch by id and a normalised-text compare. List-and-match is the fallback only after a timeout. Define normalisation per platform at build and log the false-negative rate (G4A.1). Never add a visible marker to a client's post. |
| S02-11 | minor | architecture | **Scheduling and revocation do not meet.** Facebook can hold a scheduled post on its side (SPV V-10). If the fleet uses that, the manifest `kill_switch` cannot recall it. Thirty identities fired at one minute is also a burst; no jitter rule exists, and the research says jitter's value is unverifiable (GEMINI-AUDIT 9.07; SPV V-13). | Schedule on the fleet side only, never platform-side. Spread each item inside its window by a per-identity offset. Say that the value of the spread is unverified. |
| S02-12 | minor | hermes | **Evidence volume and guidance.** FE writes a run note per job. Under the assumed workload that is 90 notes a day with three platforms live and 150 with all five, each needing a `job` call and a file write by the model, for jobs the profile never started. FS has no campaign guidance (per-account variants, media constraints, what to do when a platform is blocked). | For scheduler-run jobs, write only the daily note, plus run notes for failed or uncertain jobs. Add campaign and per-platform content constraints to FS once S02-1 and S02-2 exist. |

## Where DECISIONS looks wrong or silent

- **D13** says content comes from "an approved campaign manifest" but D17 has no tool to create one (S02-1).
- **D2** says "identical posts across client accounts" is never built. The red line and the platforms' rules
  reach further than "across clients" (S02-5).
- **D12** has no X fee line and no model of API-only accounts (S02-6; X is C-17).
- **D3** makes the IP part of an identity at creation. For an account that will never open a browser that is a
  cost with no benefit (S02-6).
