# S10: self-hosted Steel cannot pass a hard site, so a new identity is homed on Browserbase

Role: scenario stress-tester, group 4. Walked against the drafted design: `fleet/DECISIONS.md`,
`fleet/ARCHITECTURE.md`, `fleet/CHARTER.md`, `fleet/SOUL.md`, `fleet/MILESTONES.md`, `fleet/docs/**`,
`fleet/hermes/**`. Nothing here is built. Every step below is "what the design says would happen".
Where the design is silent, the step says so.

**Verdict: breaks.** Three things fail, and each one is a design hole, not a missing detail.

1. The only gate for choosing Browserbase (reason R1) cannot tell a *functional* failure (Steel cannot
   render or log in) from a *defence* failure (the site is deliberately refusing automation). For the
   second kind, moving to another stealth stack is the work-around the charter and the lead-gen playbook
   forbid.
2. The move itself ("a new identity and a fresh human login") has no mechanism. The registry forbids
   binding one account twice, retirement destroys the state the move depends on, and everything an
   operator approved is keyed to the old `identity_id`.
3. Charter invariants 3 and 9 cannot hold on a Browserbase home as written, and nothing in the charter
   says so.

DECISIONS.md D11 is not wrong, but its trigger sentence ("a site where Steel fails") is too loose to build
a gate from. It needs the functional/defence split below. This is reported here, not silently changed.

---

## 0. Setup and assumptions

The request says "one client", "a hard target site", "a NEW identity on Browserbase", "BYO proxy".
The design has more than one kind of "hard target", and they get different answers. I walk one main
path and branch where the answer differs.

| Item | Value used in the walk |
|---|---|
| Client (tenant) | `acme` |
| Identity | `acme-portal`, `kind: account`, `infra_home: steel-oss`, one dedicated static ISP IP, persona `honest` |
| Hermes profile | `acme-ops`, token bound to `acme-portal` with scopes `read`, `draft` |
| Hard site | `portal.example`: a non-social web application where the client is an authorised user (a supplier or marketplace portal). A scheduled procedure `portal.download_invoices` (kind `browser`, read-only) runs against it. |
| Failure on Steel | The site answers the identity's browser with a bot-defence interstitial or a 403 after the page loads. |
| Branches | **B-F** the failure is functional (a login the Steel viewer cannot complete, a page that needs a feature Steel's Chromium lacks). **B-D** the failure is a deliberate bot defence. **B-P** the "hard site" is a social platform and the failure is a checkpoint, restriction or ban on the client's account. |

Which branch applies is the most important unknown, and the design never asks for it (gap G10-1).

## 1. Walkthrough

### Step 1. The failure appears (Hermes: `run`; fleetd run engine; node executor)

1. A manifest-free scheduled job fires. The scheduler pre-wakes `acme-portal` (ARCHITECTURE §4.11), the
   wake flow W1-W13 runs (§4.1), the login probe for `portal.example` passes.
2. `run` executes `portal.download_invoices`. Step 3 loads the invoice page. The executor climbs the
   ladder (§4.3): L0 locator misses, L1 has no entry, L2 builds candidates from a snapshot of the
   interstitial page, L3 `observe` is tried through the model shim.
3. The deterministic blocker responses in §4.2 step 6 are `login_wall`, `checkpoint`, `captcha`,
   `consent_dialog`/`popup`, `no_change`. A Cloudflare-style "checking your browser" page, a 403, or a
   "your session looks automated" page matches **none** of them unless the decider happens to label it
   `captcha`.
4. Result for the profile: most likely `step_failed` (§5.5: "a step failed after the whole ladder"),
   possibly `checkpoint` if the page contains a challenge.

What the design does not say:

- **No blocker class for "the site refuses this browser".** There is no `site_blocked` result, no
  per-(identity, host) back-off and no circuit breaker. The lead-gen playbook has the rule for research
  identities (`docs/playbooks/lead-gen.md` §3.8: "Stop that domain, back off, set a cool-down"), but the
  architecture's `account` path does not. The next scheduled run wakes the identity and hits the site
  again from the same IP.
- **A `checkpoint` answer pauses the whole identity** (ARCHITECTURE §3.8, `identity-and-proxies.md` §2.5:
  two close together send it to `quarantined`). Granularity is the identity, not the site. If the
  identity also holds another platform login, a wall on `portal.example` stops that work too.
- If the L3 model is shown a click-through challenge, the only thing between it and the box is the
  `blocker` decider label and the "agents never solve CAPTCHAs" rule. The executor's refusal list in
  §4.3 covers password and OTP *fields*, not "I am human" checkboxes.

What the human sees: nothing yet. What the agent sees: `step_failed` with rung history in `details`.

### Step 2. The profile reports (Hermes skill `fleet-router`, tool `feedback`)

`fleet-router` says: report `step_failed` with `feedback`. The profile calls
`feedback{kind:"blocked" | "other", job_id, note}`. The fleet records it. The profile writes a run note
(`fleet-evidence`) and lists the job under **Needs a person** in the daily note.

What the design does not say:

- `feedback` only quarantines **procedures and L1 entries** (§5.3 tool 14). A blocked *site* is not a
  procedure fault. Nothing aggregates "this host fails on `steel-oss` for N identities". No record exists
  to hold the R1 evidence that `browserbase.md` §8.1 asks for ("a measurement note").
- The notifier (C16) lists `needs_reauth`, `checkpoint`, `needs_approval`, uncertain effects, drift,
  upload failure and budget caps. It does not list "repeated step failure on one host". Where the owner
  hears about this is AQ-3 (open).

### Step 3. Triage: which kind of failure is it? (Owner; no tool; no component)

This is where the design should branch and does not.

| Branch | Example | What the design's own rules say | What D11 / `browserbase.md` §8.1 R1 says |
|---|---|---|---|
| **B-F** functional | Passkey or IME login the Steel viewer cannot complete (D4: untested); page needs a feature the headless build lacks; memory blow-ups | Fixing it is engineering. A new home is a legitimate remedy if Steel truly cannot do it. | R1 allows it ("includes a login that Steel's viewer cannot complete") |
| **B-D** defence | Bot wall, IP or fingerprint reputation block, "automated traffic" page | `docs/playbooks/lead-gen.md` §1.2: no "stealth or proxy-rotation feature to get past a block". §3.8: "No IP rotation, no proxy change, no User-Agent change to get through." D9: "continuity, not evasion". | R1 allows it if "Steel with the same vetted proxy and persona failed, Browserbase with the same proxy passed". That test result *is* proof the Browserbase stack beat the defence. |
| **B-P** platform restriction | Instagram/Facebook/TikTok checkpoint, restriction or ban on the client account | `identity-and-proxies.md` §3.7: "the fleet does **not** answer with a new IP or a new identity. That is ban evasion, a red line." Charter escalation: "a platform restricts, warns or suspends an identity (stop all activity on it; no work-around)." | Not excluded. R1 does not mention it. |

Reading Browserbase's own pages makes the B-D problem concrete. Browserbase sells "automatic
fingerprinting (devices, locales, operating systems)" on non-Verified sessions and says the OS is always
Linux (`https://docs.browserbase.com/platform/identity/verified-customization.md`). The fleet does
not know what that fingerprinting changes (`browserbase.md` §2.5: "Whether a plain session already
presents altered device, locale or OS values is unknown"; the doc itself ties this to Q-04, the spoofing
question). So **passing where Steel fails may be exactly the vendor's undeclared spoofing**, and the fleet
would be adopting it by renting it. Q-04 is "pending, default: no spoofing". R1 can be satisfied without
anyone answering Q-04.

Required outcome of triage (not in the design): classify the failure as B-F, B-D or B-P, record it, and
only B-F continues. B-D stops with an owner decision: ask the site for permission or an API, or have the
client's own person use the site by hand (human in the viewer). B-P stops under the red line.

Gap G10-1 below.

### Step 4. Gathering "R1 evidence" (Owner; Browserbase key; test pages)

R1 wants: "a measured run on a sacrificial account or public test page: Steel with the same vetted proxy
and persona failed, Browserbase with the same proxy passed. Never measured on a client account."

Problems when I try to follow it:

1. **"Sacrificial account" on a social platform is a fake account.** The charter red line is "fake accounts
   or personas". On `portal.example` a test account may breach that site's terms. So the evidence has to
   come from public pages, which cannot reproduce a logged-in defence (cookies, account age, behaviour).
2. **"Same vetted proxy" and "same persona" cannot both be true on two homes.** Each identity has a unique
   IP (`proxies.exit_ip` is unique; `proxy_id` is 1:1). A test that borrows the client's live IP from a
   second browser mixes two fingerprints on one IP, which D3 and `fleet-identity` ("two browsers mean two
   fingerprints and two IPs, and that is what gets accounts locked") say not to do. A test on a spare IP
   is a different IP, so it is not "the same proxy". On the persona side, Browserbase cannot pin the user
   agent or locale (`browserbase.md` §3.6), so "same persona" is unreachable.
3. **The test config must be the production config.** Browserbase solves CAPTCHAs by default
   (`https://docs.browserbase.com/platform/identity/captcha-solving.md`). The fleet sets
   `solveCaptchas:false` (charter invariant 4), but **D11 does not say so** and `browserbase.md` §8.1 does
   not require the A/B to run with it off. A pass that depended on auto-solve would not survive in
   production. (The charter and identity page already note the D11 gap.)
4. **Prerequisites to run any test at all:** a Browserbase plan and key (none exists; `MILESTONES.md` MB
   "Depends on"; Q-12 is the hands-on gate, Q-06 caps are $0 by default), the M2 infra adapter (MB depends
   on it), and Justin's yes (charter: "Buy or apply for ... a Browserbase account").

So, today, step 4 cannot be performed by anyone, and the rule as written cannot be performed even later.

### Step 5. The decision (Owner only; operator console; no agent tool)

`browserbase.md` §8.2 lists eight preconditions. Checked against current defaults:

| # | Precondition | State under defaults |
|---|---|---|
| 1 | Owner approval (Q-12 for a paid key) | Not given. Default: no droplet, no key. |
| 2 | Vetted static ISP IP with an **HTTP/HTTPS** endpoint and a single-IP credential | No IP bought. SOCKS5-only vendors are out. |
| 3 | A Q-07 answer that allows client page content, files and the Context to live in a third-party hosted browser | **Charter default for Q-07 is silent on hosted browsers.** It says DM content is not sent to a *model provider*; Browserbase is not one. Treat as "not allowed until answered" (gap G10-7). |
| 4 | Client's written risk acceptance (Q-01) plus the Browserbase ToS note | Not on file. |
| 5 | A plan with the needed concurrency; keepAlive verified | Plan gate is contradictory across three sources (`browserbase.md` §2.3, V-3). |
| 6 | Written re-login path | Not written. |
| 7 | Spend cap for the home (Q-06) | Default $0. |
| 8 | Canary rule passes (O-13) | Not run. |

Two more constraints from Browserbase's terms (`browserbase.md` §6): outbound-message procedures (DM,
comment, reply) do not run on Browserbase-homed identities by default, and BB-O2 (ask Browserbase in
writing whether a client's authorised use is within intended use) is open. BB-O1 (accept the weaker
IP-pin controls or build Option F, a fleet-run edge forwarder on a public host) is open and **is not one
of Justin's 14 questions**.

Result: under today's defaults the decision cannot be "yes". The honest answer to the client is "this
portal cannot be automated yet; a person can use it through the viewer on the existing identity". See
S12 for what that costs.

### Step 6. Create the new identity (Owner; `identity-and-proxies.md` §2.1; registry C3)

Assume every precondition is met later. The creation steps are `identity-and-proxies.md` §2.1 steps 0-7 and
`browserbase.md` §3.1, §8.4.

| Part | What happens on a Browserbase home | Problem |

| Registry binding | `identity_platforms` has **unique `(platform, handle)`, "so one account can never be bound twice"** (ARCHITECTURE C3, §3.3). The new identity needs the same pair. | The insert fails while the old identity holds the binding (G10-3). |
| Persona | Browserbase can pin only viewport, region, timezone (by a CDP override), and the proxy IP. It cannot pin user agent, OS, locale or hardware (`browserbase.md` §3.6). ### Step 7. First login through Live View (Operator; viewer broker; Browserbase Live View)

`browserbase.md` §3.7: create a session with `persist:true`, hold fleetd's anchor CDP connection, mint a
Live View link with a short `expiresIn` (60-21,600 s), show it **only to the human**, human logs in,
login probe, `REQUEST_RELEASE`, wait, mark ready.

Walk-through issues:

- **Which link does the agent get?** ARCHITECTURE §4.8 step 2 and §5.3 `identity_control reauth` return a
  viewer URL in the tool result so "the agent can pass it on". `browserbase.md` §3.7 says the Live View
  link is "never put in an agent's context, a log or a tool result". Both can be true only if the agent
  receives a fleetd *ticket* URL and the Browserbase debug URL is minted server-side after the operator
  authenticates. Neither document says that. Browserbase's debug URL is a bearer capability
  (`https://docs.browserbase.com/platform/browser/observability/session-live-view.md`; `browserbase.md`
  §2.7 `inference`). Operator authentication is still open (AQ-1), so this step is blocked on AQ-1 (G10-8).
- **Viewer classes are untested on Browserbase too** (`browserbase.md` §12 item 12): Enter, Backspace, Tab,
  arrows, IME, passkeys, native dialogs, HTTP auth, file pickers. If the reason for moving was a login
  Steel's viewer could not complete, there is no evidence the Browserbase viewer can.
- **Fencing.** The human "holds the identity lease" but Browserbase does not enforce it; fleetd does
  (`browserbase.md` §3.7). The node agent cannot cut a remote session (ARCHITECTURE §3.5 "weaker fencing");
  takeover ends the session through `REQUEST_RELEASE`, which also ends the agent's.
- **Persistence timing.** The Context saves "when the session closes"; the doc says "wait a few seconds"
  (`https://docs.browserbase.com/platform/browser/core-features/contexts.md`). Steel's 30-second cookie
  commit window (D4) may also apply inside Browserbase's Chromium. Unknown. GB.1 should include a cookie
  written seconds before release, as G1.1 does.
- **First login is a new device from a new place.** Expect a verification step. The client's person with the
  second factor must be present (`identity-and-proxies.md` §2.2). The client must be told first (§3.7).

What the human sees: a fleetd page with an embedded Live View. What the agent sees: `identity_status` for
the new alias shows `needs: reauth`, then `state: awake`, `auth.state: ok`, a new `auth_epoch`.

### Step 8. Canary and first real run (fleetd; canary rule O-13; `MB` gates GB.1-GB.3)

The new identity is `quarantined`-or-canary until it passes S2 (read-only first). Then the first
`portal.download_invoices` run, verified by the procedure's verifier.

What `MB` actually measures: GB.1 (59 sessions login survival, exit IP stable), GB.2 (timezone across
reconnects and Live View), GB.3 (restore from CDP snapshot). It does not measure: the thing that triggered
the move (does the hard site now pass, with `solveCaptchas:false`, over many days?); user-agent and
fingerprint drift across sessions on one Context; WebRTC/DNS leak; exit-IP pin enforcement; the Live View
input classes; the guard over remote CDP; the cost of BYO-proxy bytes.

### Step 9. Cutover: the profile starts using the new identity (provisioner; bindings; scheduler)

Everything an operator set up is keyed to the old `identity_id`:

| Object | Keyed to | What cutover must do | In the design? |
|---|---|---|---|
| `bindings` (token x identity: scopes, caps) | `identity_id` | Create for the new identity | Implicit (provisioner), not specified |
| `schedules`, queued `jobs` | `identity_id` | Re-point | No |
| `manifests` and `approvals` (`manifests.identity_id`; approval `subject` names the account) | `identity_id` | Re-approve as new revisions for the new identity | No. `supersedes` exists only within one identity |
| `effects.effect_key = H(identity_id, task_id, kind, target, content_hash)` | `identity_id` | Carry or re-key committed and uncertain effects | **No.** Same intended post under the new id gets a new key, so the ledger's duplicate protection does not cross the move (G10-3) |
| `l1_entries` | tenant (default) | Reuse. Good. | Yes (§3.9) |
| `auth_markers`, `risk_acceptances` | identity / tenant+platform | Recreate / reuse | Partly |
| Hermes profile instructions, notes, cron prompts | alias string | Repoint | No (G10-4) |

While the old identity is `quarantined`, its alias answers `quarantined`. `fleet-router` tells the agent to
"stop and tell a person" on `quarantined`. So until someone re-points everything, each scheduled run
produces a stop-and-notify, which is correct for a hold and wrong for a planned move.

### Step 10. What happens to the old identity (owner; `identity-and-proxies.md` §2.6)

The design has two possible answers and no rule for choosing:

- **Quarantine** ("no work, no wake, reversible"): keeps the bundle, so it is a rollback. But the unique
  `(platform, handle)` binding blocks the new identity from existing at the same time, and "no wake"
  means nobody can use the old session to log out of the site.
- **Retire** (terminal): resolve holds, revoke platform connections, ask the client to remove the fleet's
  device from the account's security settings (a person does it), destroy every bundle generation and the
  data key, do not renew the IP term, revoke bindings, keep evidence per retention, never reuse the id.
  Rollback is gone. If Browserbase then fails the canary, nothing can pass the hard site and the old login
  is destroyed.

Proposed order (dependencies, not dates): quarantine old, run the new through its canary gate and one full
scheduled cycle, then retire old. This needs a `superseded_by` link, a partial unique index on
`(platform, handle)` over *active* bindings only, and an explicit `retire` precondition: "successor has
passed canary". None exists (G10-3).

Costs left behind: the old IP's remaining term (sunk; `term_expires_at`, D10 "bought on a term"), the old
node slot (freed), 30 days of hot evidence and 1 year of audit (estimates, ARCHITECTURE C15), and, if the
site enforces one session per user, the new login kills the old session, which is useful.

### Lock-in, stated once

Browserbase gives no way back. Contexts cannot be listed, exported or uploaded through the self-serve API,
and the CDP snapshot of cookies and localStorage misses IndexedDB and service workers (`browserbase.md` §5).
Moving this client back to Steel later is therefore **yet another new identity and another fresh human
login**, and a Browserbase suspension voids every Context at once. The owner must be told this before the
first Browserbase identity exists, in the same checklist as the continuity trade-off (G10-5).

### Pending Justin: Q-13

Cross-client unlinkability **cannot be assessed on this home** without hands-on (`browserbase.md` §3.6,
**pending Q-13**). Browserbase picks the hardware and fingerprint values and they are unknown. The
decision checklist must not promise a client that a Browserbase-homed identity is unlinkable from other
clients' identities. Q-01, Q-04, Q-06, Q-07, Q-12 and Q-13 all sit on this one decision; the default for
each is "not given".

## 3. Cost (estimates; sources named)

One identity on the new home, monthly:

| Line | Amount | Source |
|---|---:|---|
| Browserbase Developer plan | $20 | `https://docs.browserbase.com/account/billing/plans.md` (official-docs) |
| Browser hours | 0 extra up to 100 h/month; $0.12 per extra hour | same |
| Dedicated static ISP IP | about $2.5-3.3 | vendor claim, `docs/identity/identity-and-proxies.md` §3.2 |
| BYO-proxy bytes billed by Browserbase | **unknown** (`browserbase.md` §12 item 1) | not documented |
| Models | unchanged: the fleet's callback | D6 |
| **Running total, one identity, 30-100 h/month** | **about $23** | estimate |

If keepAlive is needed and only the Startup plan allows it: $99 + IP, about $102 (estimate; the gate is
unknown). These are small. They are not the cost that matters:

- **Fixed floor.** The first Browserbase identity pays the whole plan. D12's per-identity Browserbase column
  does not apply to one identity.
- **Unbuilt work.** The `MB` adapter (session factory, anchor connection, per-Context lock, timezone check
  on every page, snapshot at session end) depends on M2. If Option F (BB-O1) is chosen, a public service must
  be built and defended.
- **Sunk costs.** The old IP's remaining term. The client's person's time. The owner's decision time.
- **Risk cost.** Browserbase may suspend "for any or no reason" and a suspension invalidates *all* Contexts
  (`browserbase.md` §5, BB-3): every Browserbase identity needs a fresh human login at once. That is a fleet
  event, not a per-identity cost.
- **Spend caps.** Q-06 defaults every cap to $0, so even $20 is blocked until Justin names a number.
