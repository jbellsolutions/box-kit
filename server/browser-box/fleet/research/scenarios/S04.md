# S04: lead generation for 200 target companies, no paid enrichment

Role: scenario stress-tester, group 2. Nothing in the fleet is built, so this is a paper walk of the drafted design
as if it were running. It follows DECISIONS.md where DECISIONS and the dossiers differ.

**Verdict: handled-with-gaps.** The cascade logic (tier 0, then `extract`, then `task`, goal-keyed escalation, grounding, evidence) is
the most carefully specified part of the lead path. Three things stop it running as written: (1) under the plan defaults
it is refused at the start (MS N-4), (2) the input "200 companies" only works if the owner supplies domains, because
discovery is an admitted hole, and (3) the architecture does not contain the components the playbook and the charter
rely on (robots.txt, source registry, per-field evidence, batch jobs, an HTTP-only research wake). For a **names-only**
input the scenario **breaks** (no sanctioned way to find the sites).

## The scenario, pinned down

Justin tells a Hermes profile: "Find contact data for these 200 companies." No Clay, Apollo, Hunter, ZoomInfo or any other
paid enrichment (CH red lines table; his standing rule). The agent does the enrichment with the fleet's own browser.

I walk the case the playbook can serve: **the owner supplies 200 company domains** (LG §1.1, §3.10). The name-only case is
step 2. Assumptions (mine, flagged): one tenant; the tenant has one `research` identity; Answer A of Q-01 (API-first),
which does not change this scenario because lead generation is a browser use under both answers (ARCH §8.1);
`contacts: role_only` (LG §4.4); Q-07 default (public company pages may go to the allowlisted reasoning provider; no DMs
are involved).

## Walkthrough

### 0. Preconditions the design itself sets

- **N-4 is "not allowed".** MS §5.4 N-4 and LG banner: no live run on a real company website until Justin says yes.
  The same sentence in CH "What agents may do" says the opposite ("Research the open web, read-only: public company
  pages"). A profile that reads the charter will start; a fleet that reads MS will refuse. This walk assumes he said yes
  to N-4. (Gap S04-1.)
- **M3 is done** (the `extract`, `task`, `run` tools are listed only from M3; MS §2.3), **Q-12** answered, a `research`
  identity exists with its dedicated static ISP IP (IP §3.1, §3.8: about $2.5-3.3 per IP-month, vendor claim, bought on a
  term). Creation is owner-only (ARCH §3.2, D17).
- **Nothing here is built.** The source registry, lead record, consent ledger, `research` identity, `fleet-leadgen` skill
  body and the per-field-evidence `extract` result are all `design` (LG status ledger).

### 1. Hermes entry: which skill, which first call

1. Profile loads `fleet-router`; first call `fleet_status` (token, tools listed, budget, `skill.ok`). Component C1 doors, C2
   auth. Writes: `audit`. Human sees nothing.
2. `fleet-router` table row "Leads from the open web" sends it to `fleet-leadgen`. The skill says: use a `research`
   identity, never an `account` identity; call `identity_status`; if none, ask the owner.
3. `identity_status` (read-only) returns `acme-research` with `kind: research`, `state: asleep`.

### 2. Input and discovery

- If Justin supplied **200 domains**: continue.
- If he supplied **200 company names**: there is no step. LG §3.10 says discovery is "the research does not say how the
  agent finds the site", not scraping a platform, not scraping a search engine's results, not a bought list, and "until
  that table exists, discovery is owner-supplied lists only". The Skill does not say this (it lists "public
  directories, public registers" as allowed). `task` could be told "find the website of Foo Ltd", but its `allowed_hosts` is a
  caller-supplied domain list (ARCH §5.3 tool 8), and Browser-Use would go straight to a search engine, which LG
  forbids. **The scenario as worded breaks here for names.** No milestone owns the discovery research task (grep of MS for
  "discovery": none). (Gap S04-2.)

### 3. Fan-out: how 200 domains become work

The design offers two routes (LG §5):

- **Route 1, preferred:** a read-only procedure `open-web-contact-extraction` run through `run`; the goal check runs in
  fleetd code. But `run` takes one `identity`, one `procedure`, one `fields` object (ARCH §5.3 tool 5). There is **no
  batch or campaign construct**: job kinds are `wake|sleep|run|act|extract|task|publish|reconcile|reauth|maintenance`
  (ARCH §3.9); `parent_job_id` exists but no semantics are written for it (campaign cap, cancel-all, partial results,
  resume). So 200 domains means 200 `run` calls, each returning a `job_id` inside the 90 s budget, then 200 polls.
- **Route 2, what the written skill does:** Hermes sits between the tiers: `extract via:"http"`, then `extract via:"browser"`,
  then `task`. LG §5 says this route cannot run the goal check in code unless `extract` returns the goal verdict, and ARCH
  §5.3 tool 7 does not. The skill itself says robots.txt, UA and pacing are "a requirement, not yet in ARCHITECTURE 4.4".

Per company that is at least: 1 `extract` + 1 or more `job` polls + 1 note write. For 200 companies: about 600-1,200 Hermes
tool turns (`estimate`, 3-6 per company). A Jev trial employee has a small capped turn budget in iterations and tokens (ARCH §4.0
item 4, HP missed issue 3): it cannot do this at all. (Gap S04-5.)

**Concurrency.** One running job per identity (ARCH §3.9, the claim locks the identity row) and a lease with purpose `work`
(§3.5). The design never says whether a **tier-0 fetch needs the lease**. If yes: 200 companies run **serially** on the one
`research` identity, whatever LG §5 says about "several domains in parallel inside the page and politeness limits". If no:
the fetch bypasses the one-writer rule on an identity that may be waking. Either answer is a design choice that sets the
wall-clock; neither is written. Parallelism then needs N `research` identities, each with its own IP (about $3 per
IP-month each) and slot. (Gap S04-5.)

### 4. Tier 0, per domain (L0, no model)

1. Source registry lookup (LG §4.5): is the host `disallowed`, `blocked`, `do_not_research`, or an unapproved third-party
   source? **There is no `source_registry` table in ARCH §3** and robots.txt appears nowhere in ARCH (grep: only CH red-line
   row, MS rows and LG).
2. Fetch and cache robots.txt for the fleet's bot token and `*`. On a network error or `5xx`: do not fetch (LG §3.5; the
   spike treated unreadable as allow).
3. One GET through the identity's forwarder, bot UA, 2 MB cap, 15 s timeout (spike values; politeness numbers are
   `to measure`, LG §8 item 6). Parse JSON-LD, `mailto:`, `tel:`, links; follow same-domain contact/about/team/impressum
   links to the page limit (unset). Never fetch platform hosts; record them as URLs with `fetched:false`.
4. **Who runs it and through what?** ARCH §4.4 step 2: "The node agent fetches through that identity's forwarder, no
   browser woken." But the forwarder lives in the `identity-runtime` container, which joins the Steel container's network
   namespace (ARCH §2.2, W7-W9: network, Steel, then runtime, then IP check). SP §8.1 has a holder container so the
   forwarder can be up before Steel (steps 6-8), which would allow an HTTP-only mode, but **neither document defines an
   HTTP-only wake**. As written, a tier-0 fetch needs a woken identity: the 11.7-21.6 s floor plus bundle download, then,
   at the end, the sleep path: at least 31 s cookie-quiet hold, tar, encrypt, upload, compare-and-set (ARCH §4.9; SP §8.2),
   for an identity that never logs in and has nothing worth persisting. (Gap S04-4.)
5. Goal check in code: are `required` fields met with grounded evidence? Yes: stop, record tier 0.
   Evidence written per datum (LG §4.2): URL, `fetched_at`, tier, method, quote, `content_sha256`, robots result.

What the human sees: nothing yet. Cost: $0 model; the spike measured 70-344 ms per page from a Mac with no proxy on 5 public
test pages (SPK, `hands-on`, n=5). **The claim "most contact data is static HTML" is unmeasured on company sites** (every live
test page returned empty JSON-LD, mailto, tel; only the author's fixture was populated; LG §0 item 9).

### 5. Escalation (code, not a model)

Per LG §3.4 table: wall (login, CAPTCHA, 403, 429, off-domain redirect, paywall, consent wall) stops the domain and records
`blocked`/`disallowed`; no stealth, rotation or solver. Not met and a known contact/about/team page exists: tier 1. Not met
and no known page: tier 2. Cap reached: `goal_unmet`, no retry on a stronger model.

Expect a share of the 200 to end `blocked`: sites behind a bot challenge will refuse a plain HTTP client, and the fleet is
forbidden to try harder (LG §1.3 rule 5, §3.8). That is a correct outcome, but no one has measured how many; the owner gets
a partial list.

### 6. Tier 1: Stagehand `extract` (L3, generative)

1. `extract(identity: acme-research, instruction, schema ≤ 20 KB, url, via:"browser", locator)` (ARCH §5.3 tool 7). Submits a job;
   wake stage first (ARCH §4.1: W1-W13; W12 login probe for a research identity has no site to probe: unspecified).
2. Executor navigates through the Guard (security.py classifier, ARCH §2.3). **robots.txt before top-level navigation is
   in LG §1.3 but not in the Guard or executor spec**, and links the page navigates to by click are not "navigate" actions.
3. Stagehand v4 `extract`: 2 model calls (Extraction, then Metadata), via the shim to GLM 5.3 Flash
   (`https://docs.stagehand.dev/v4/basics/extract.md`; SH §5.1: 2.0 s, 2,403 in / 178 out tokens, $0.00026 on one easy
   page). Output validated against the caller's schema by the shim.
4. **Grounding check** (LG §4.3): the quote must be a substring of "the stored source of the same run" after NFKC and
   case-fold. The stored source for tier 1 is "the accessibility snapshot Stagehand used" (LG §4.3 rule 1). But Stagehand
   does not hand that snapshot back from `extract`; the executor would need a second `page.snapshot()` that may differ from
   what the model saw; and SH §12 says the default is to store a snapshot **hash**, not the tree, "until an
   evidence-retention policy" exists, which DEC does not yet have. (Gap S04-9.)
5. Lead record and per-field evidence: **the `extract` result has no field for them** (`{data, source, untrusted}`; LG §9 row 6
   admits it).

### 7. Tier 2: Browser-Use `task` (L4, many generative calls)

1. `task(identity, goal, start_url, mode:"read_only", max_steps ≤ 8, max_usd, allowed_hosts:[company domain], output_schema)`.
2. Engine mutex, own OS process, hard kill timer, `Tools(exclude_actions=[upload_file, save_as_pdf, evaluate])`,
   `highlight_elements=False` (ARCH §4.5). Gate G runs in `register_new_step_callback` before each action.
3. **Boundary claim does not hold as written.** LG §3.7 says `allowed_hosts` is enforced by "the guard and the network rule".
   The network rule allows exactly the proxy `IP:port` (ARCH §6.3), so it cannot enforce a domain. The Guard has a static
   deny list and has no per-task allow-list in ARCH §2.3 or §6.4. A per-task allow-list must permit third-party sub-resources
   (fonts, CDNs) while refusing top-level navigations off-domain: not specified. (Gap S04-6.)
4. **Search boxes.** Gate G's read-only allow-list permits "text into search boxes" (ARCH §4.3). LG §3.7 says search boxes
   are not used on company sites, because submitting is a form post, and enforces this only by "not granting `publish`/`dm`".
   A read-only token still types and submits a search. The classifier backstop fails open on icon buttons. No lead-gen mode
   exists in gate G. (Gap S04-6.)
5. **Platform hosts.** `extract` and `task` are listed from M3 (MS §2.3). The refusal for "platform scraping for leads" is
   G4.6, in M4. `url` and `allowed_hosts` are caller arguments. Between M3 and M4 nothing refuses a call aimed at a platform
   host from the research IP. (Gap S04-7.)
6. Cost: $0.0013-$0.0033 per task on easy Steel pages (BU §16, `hands-on`); a 20-step dense run could reach about $0.04
   (`estimate`, BU §16). 7-8% of dense-page click acts were defective, with 34-52 s runaways at an 8k cap (CONSISTENCY C-22):
   tier 2 time has a heavy tail.

### 8. Output: the lead record, the note, the human

1. fleetd assembles `lead.v0` per company (LG §4.1): values with evidence, `goal.status`, `trail`. Dedupe key `lead_id` =
   hash(tenant, registrable domain). **No `leads` table exists in ARCH §3** ("Other tables, briefly" lists spend, evidence,
   decision_log, viewer_tickets, operators, nodes, audit).
2. The `job` result has one `obsidian_note` block for `Runs/<job_id>.md` (ARCH §5.3 tool 10). LG §4.6 wants 200 notes
   `Leads/<domain>.md`. The only writer is Hermes: "the skill writes the company note beside it" (LG §4.6), i.e. a model
   writes 200 files through file tools. A model re-typing a quote can paraphrase it, which silently voids the grounding
   guarantee at the last step. The Skill names `Leads/<company-slug>.md` and has the model write "one line on what they do,
   in your words"; LG says `Leads/<domain>.md` and says nothing of model prose. (Gap S04-10, S04-11.)
3. Evidence blobs carry `expires_at`; ARCH C15 gives 30 days hot (`estimate`). The note stores opaque
   `fleet-evidence:ev_...` refs, which resolve only while the blob lives. LG §4.6's own test: "Justin can open the vault and
   follow a quote back to its source." After the evidence expires the ref is dead. (Gap S04-9.)
4. There is no CSV or table deliverable. A client wants 200 rows, not 200 notes. (Gap S04-10.)
5. What Justin sees: the Hermes reply, the vault notes, the `Daily/` note listing jobs; blocked and disallowed domains are
   listed with reasons (LG §3.8). The fleet's notifier is not involved unless a budget cap is hit.

### 9. Sleep, accounting

Sleep path as in step 4; spend ledger settles per model call (C13). Cost lines are per job; there is **no campaign-level
cap** across 200 child jobs, only per-job `budget`, per-identity, per-tenant and fleet caps.

## Cost and System-1 share, worked

### Cost (all `estimate` or `assumption`; no company site has been run)

Unit figures: tier 0 $0 and 0.07-0.34 s per page (SPK); `extract` $0.00026 on an easy 2.4K-token page, about $0.001 per model
call on a dense 6K-token page at list price ($0.15/M in, $0.50/M out; SH §5.1 "an uncached act cost $0.00095"), so about
$0.002 per `extract` (two calls); `task` $0.0013-$0.0033 easy, about $0.04 dense 20-step (BU §16).

| Case (assumption) | Model fees | Notes |
|---|---:|---|
| Every domain resolved at tier 0 | $0 | Best case; unmeasured |
| 60% tier 0, 30% tier 1 (2 pages), 10% tier 2 (dense) | 60 × 2 × $0.002 + 20 × $0.04 = $0.24 + $0.80 ≈ **$1.04** | Illustrative mix, not a forecast |
| Every domain climbs to tier 1 (2 pages) and tier 2 (dense) | 200 × $0.004 + 200 × $0.04 = $0.80 + $8.00 ≈ **$8.80** | Upper bound on these unit prices |

So **model spend is between $0 and about $9** for 200 companies. It is not the cost driver. What is:

- **One dedicated ISP IP** for the `research` identity: about $2.5-3.3 per IP-month, vendor claim, bought on a term (D10). For a
  one-off 200-company run this is the largest line.
- **Node time**: one slot. Serial wall-clock `estimate`: tier 0 about 200 × 4 pages × (0.3 s + an assumed 1 s politeness
  delay) ≈ 17 min; tier 1 60 companies × 2 pages × about 8 s ≈ 16 min; tier 2 20 tasks × 60-90 s ≈ 20-30 min; total about
  1 hour. At $0.143/hour (bundled $96/month) that is cents; with Q-13 (one client per node) it may be a node of its own
  (MS §7.5). Wake overhead and the 31 s sleep hold add per wake. All `to measure` (G1.7, G5.5).
- **Hermes-side model turns**: 600-1,200 turns on Hermes' own model under the Skill route. Its price is not in the research
  and the fleet's ledger cannot see it (S1 §6.1: "Hermes' own model is invisible to this metric"). This probably exceeds all
  fleet costs combined (`inference`, `to measure`). Route 1 collapses it to a handful of calls.
- **Q-07 default** (ZDR routing): changes the provider allowlist and invalidates the bench (DEC D8). Prices may move by a small
  multiple; irrelevant at these volumes.
- **Human time**: reading 200 notes, deciding what to do after `blocked`.

### System-1 share

Definitions (S1 §6.1, MS §4.5): *System-1 share* = actions finished at L0, L1 or L2 / all **browser actions**, where a browser
action is one executor command. Consequences for this scenario:

- **Tier 0 is outside the metric.** It is a node-agent HTTP fetch, not an executor command (ARCH §4.4 step 2). The design's best
  outcome, a company resolved with zero browser and zero model, contributes nothing to numerator or denominator.
- **Tier 1 `extract` is L3 by construction.** A decider cannot extract text (ARCH §4.3). The value-producing step is always
  generative; the only L0 steps are navigations. Whether navigation counts changes the reading of a tier-1 page from 0% to
  about 50% (1 navigation, 1 extract).
- **Tier 2 is L4.** Every Browser-Use step is a reasoning-model call. Share about 0% apart from the start navigation.
- So the reported share for `open-web-contact-extraction` would sit anywhere from near 0% to about 50% depending on how steps
  are split ("steps per task" is already a companion metric because of that gaming risk, S1 §6.2), and it says nothing about
  the thing that matters: **what fraction of companies finished with no generative call**. The research estimate is "well
  below 90%" for lead research (DEC D7, `unverified`, S1 §6 intro); nothing here contradicts it, and nothing could confirm
  it either.
- **Where System 1 could legitimately help and is unused:** choosing the contact/about/team link among code-found `<a>`
  candidates (`pick_next_page`, S1 template list), on **public** pages (`data_class: public`, so not blocked by the Q-07 default).
  LG's tier 0 follows links by a pattern list (contact, about, team, impressum), which is English/German; a Spanish or French
  site would fall through to a generative tier where a $0.0002, 300 ms decider choice would do. (Gap S04-12.)
- Cost is not a System-1 problem here: a GLM call costs a fraction of a cent. The honest report is LG-7 (tier mix, model calls
  and cost per domain, wake time) per company, with intervals; the System-1 share is a companion number, never a headline.
