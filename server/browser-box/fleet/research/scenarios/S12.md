# S12: the client's person wants the identity in the viewer while an agent run is scheduled

Role: scenario stress-tester, group 4. Walked against `fleet/DECISIONS.md`, `fleet/ARCHITECTURE.md`,
`fleet/CHARTER.md`, `fleet/SOUL.md`, `fleet/MILESTONES.md`, `fleet/docs/**`, `fleet/hermes/**`. Nothing is
built. Clock times below are story time inside the walkthrough, not project dates.

**Verdict: breaks.** The lease and the takeover are designed for one purpose only: a human logging in
again (`needs_reauth`, `checkpoint`). A person who simply wants to use the account is outside that design.
Pushed through it, the design (1) labels a healthy identity as a lost login, (2) gives the human a lease
that has no liveness rule, so the human is either cut off mid-task or shares the browser with the agent,
(3) preempts the agent mid-effect and then lets the human's unlogged actions corrupt the very read-back
that reconciliation depends on, and (4) says nothing about the scheduled work that was displaced. The
charter promises "one identity, one writer. The holder is an agent or a human, never both"; the drafted
mechanics cannot keep that promise here.

## 2. Case A: Maria arrives first (identity asleep)

1. **Maria opens the console** and picks `acme-facebook`. There is no "use the browser" action. The nearest
   thing is reauth. Assume the console offers a takeover (§3.4 says it exists). AQ-1 (operator
   authentication) must be decided first. She authenticates.
2. **fleetd** finds the identity `asleep`. §4.8 step 3: "Wake for reauth if asleep: `purpose=reauth`, no
   workers started, no login probe." So no login probe runs at wake. The container, forwarder, exit-IP
   check and persona check run (§4.1). The floor is 11.7-21.6 s on arm64 and excludes bundle download,
   decrypt, proxy connect and node creation (`CONSISTENCY.md` C-27). Maria waits.
3. **Takeover.** fleetd runs `takeover`: token 40 -> 41, purpose `reauth`, expiry `now() + $viewer_ttl`.
   `$viewer_ttl` has no value anywhere. The node agent runs `viewer_open(identity, 41, ttl)`.
4. **What the identity now looks like to everyone else:** `lease: {holder_kind: human, purpose: reauth,
   expires_at}`; state `awake`. The notifier may treat purpose `reauth` as a lost login. The Hermes
   profile reads `reauth` and, following `fleet-identity` ("A lost login: `needs_reauth`"), may ask for a
   *second* reauth link (G12-2, G12-9).
5. **08:58-09:00.** The pre-wake finds the identity already `awake`: success, idempotent (W1).
6. **09:00.** The scheduler turns the approved, queued item into a job. The claim locks the identity row and
   tries `acquire`. The human's lease is unexpired, so zero rows: `identity_busy`. §3.9 says at most one
   job runs per identity; it does not say what happens to a job that cannot start.
   - Retry with back-off? Fail? Stay queued? Not stated.
   - The item has a window (09:00-09:30) and the approval has an `expires_at`. If Maria is in until 09:31
     the item expires. **Nobody is told.** The notifier list (C16) has no "scheduled work displaced" event. The
     Hermes profile learns it only from the next `job list` in its daily-note job. The client sees a
     missing post (G12-4).
   - If the effect were an **API** publish, none of this applies: "No browser is woken and no lease is
     needed" (§4.6). The post goes out while Maria is mid-conversation in the same account. The charter's
     "never both" covers the browser lease, not the account (G12-4).
7. **Maria does her work.** She types a reply. She also opens a second tab and checks her own mail in the
   viewer's URL bar. The guard blocks private ranges and fleet hosts only (§6.4). Nothing stops her from
   logging into other accounts inside this identity's profile, which then land in the encrypted state
   bundle (G12-14).
8. **Handback.** She presses Done. §4.8 step 7: wait for the cookie-quiet period (31 s of quiet, cap 90 s,
   §4.9 step 3; social pages rotate cookies constantly, so the cap is likely hit and the bundle is marked
   `cookies_unflushed`), run the login probe, **`auth_epoch + 1`**, store a new journal, release.
   - `auth_epoch` "increments on each successful human login" (§3.3). She did not log in. The counter now
     lies, and any rule keyed to it (login age, checkpoint telemetry) is wrong.
   - The probe checks the auth marker. It does not check which page or which Facebook identity (she may
     have switched to acting as a Page), what tabs are open, or whether a composer holds her half-typed
     text.
9. **What Maria's reply was.** It is a real effect on the client's account. It has no intent row, no
   manifest, no governor reservation, no receipt. The fleet cannot see it, by policy: "no logging of viewer
   websocket payloads and no recording of the stream" (`steel.md` §7.3 step 6). The governor's daily
   counters and the duplicate-content check will not know. If the approved item she partly duplicated runs
   later, the fleet will post it (`effect_key` matches only fleet effects, §3.6) (G12-5).

**Case A verdict.** It "works" only if every undefined value turns out benign. The mislabelled purpose,
the missing "displaced work" handling, and the unjournaled effect are all hit on the first ordinary use.

## 3. Case B: the agent run is already in the middle of a step

Token 7, run `job_882`, step 3 of 7, rung L1. The step is a browser-channel effect: composer filled with
the approved text, pre-submit hash check passed, **intent row `E1` committed**, click on Post sent.

| t | Event | Design says |
|---|---|---|
| +0 s | Maria clicks "use the browser" | Nothing warns her an agent step is live. The console shows no run state (G12-3). |
| +0 s | `takeover`, token 7 -> 8 | SQL accepts it: `WHERE fencing_token = $t_seen`. No check of identity `state` (waking, sleeping) or of an open effect. |
| +1 RPC | Node agent kills the agent's workers | "the gap between the takeover decision and the kill is one RPC [to measure, M1]" (§3.5). |
| +1 RPC | Effect `E1` (state `intent`) | §3.6: `intent -> uncertain` on "timeout / crash / **lease lost** / no receipt after grace". Treated as lost. `E1` becomes `uncertain`; the identity gets `hold(uncertain_effect)`. |
| +1 RPC | Job `job_882` | §4.8 step 1 pauses the job to `needs_human` for reauth triggers. For a takeover that is not a reauth trigger the job state is **not stated**. §4.2 step 8: pauses expire after a TTL (estimate) and then "fail with the cause's code". Which code? `identity_busy`? Not stated. |
| +30 s | Maria sees the post already live in the group. She thinks it is a mistake and deletes it. | Unlogged. The viewer shows her nothing about `E1`. |
| +2 min | Done. Cookie-quiet wait, probe `ok`, release. | The identity is `held`. Work is refused; reconcile and reauth are allowed (§3.5 purposes). |
| +2 min | Reconcile job (purpose `reconcile`) reads the group, matches `content_hash` | **Not found.** |
| +2 min | §3.6: "`uncertain -> not found after grace; pair marked safe -> reconciled_absent -> may be retried`" | The ledger reads "absent" as "never happened". It happened and a person removed it. If the platform+effect pair is marked safe, the agent posts again and undoes her decision. If not, the owner is asked to resolve with no knowledge of what she did. |

Why this is a correctness problem, not just UX: **negative read-back is the ledger's only way to decide an
effect did not happen** (D13), and a human in the same browser can make it false in either direction
(delete a real post; post the item herself so read-back finds "a match" that is hers).

What the human should see and be asked (design is silent):

1. Before takeover: "An agent step is in progress (posting to *Group X*, step 3 of 7). Take over now, or
   wait for the step to finish (recommended)."
2. After takeover with an in-doubt effect: "The agent may have posted: *<text>*. Do not repeat it."
3. At handback: "Did you post, send, delete or change anything? [list]. Did the agent's post go out?
   [yes / no / I removed it]." The answers write `channel=human` effect rows and resolve `uncertain`
   effects with `human_resolved`.

What the **Hermes profile** sees: a `job` poll answers whatever stage the fleet picks; new calls get
`identity_busy{holder_kind:"human", purpose:"reauth"}`; the skill says "wait or do other work. A human always
wins". After release it sees `outcome_uncertain` on the effect step and is told not to repeat it. If the run
came from a manifest there is no Hermes call at all: the profile learns at its next `job list`.

## 4. Case C: the lease runs out while Maria is still typing

`takeover` sets `lease_expires_at = now() + $viewer_ttl`. **Renew is for workers.** A human has no
heartbeat. Two outcomes are consistent with the text, and the design picks neither:

1. **The viewer route outlives the lease.** At expiry the scheduler's `acquire` succeeds (`lease_expires_at <
   now()`), token 41 -> 42, workers start. Maria's cast WebSocket is still open: viewer frames carry no
   fencing token, and `viewer_open(..., human_fencing, ttl)` is checked at open. Agent and human drive one
   Chromium. **Two writers.** The node agent's "kill workers on a higher token" cuts the agent, not the
   human.
2. **The viewer route dies with the ttl.** `viewer_open` has a `ttl` argument, which suggests this. Maria is
   cut off mid-sentence, with no warning and no extension. Her half-typed reply sits in a composer the agent
   may then "resume" over.

Also unspecified: reconnect after a dropped connection (tickets are single use, so she needs a new
ticket and a new takeover, and the token moves again); an inactivity timer (the node agent has "maximum
wake time and inactivity", steel-profile §9.3, which would put the identity to sleep under a person who
paused to read); takeover while the identity is `waking` or `sleeping`, when the viewer would attach to a
browser that is starting or being closed; two humans at once (a second ticket bumps the token but the first
human's route is not closed).

What the lease should be: a lease tied to **viewer liveness** (heartbeats from the viewer connection that
count input frames, without logging payloads), with an idle timeout, a maximum length, a visible countdown
with an "extend" button, and `viewer_close` called by fleetd on every token change.

## 5. Resume: what the agent walks back into

After handback, §4.2 step 8: "A job paused in `needs_human` ... resumes from its last completed step ...
because steps are idempotent except effects." That assumes the page is where the agent left it. Maria may
have navigated, opened tabs, left a draft in a composer, switched to acting as a Page, logged out, or
changed a setting. What the design offers: the pre-submit check (composer text hash and account header
must match, §4.7 step 5) and the L1 role/name re-verification (§4.3). Those protect an *effect* step. They
do not protect a non-effect step that assumes state (for example "composer is open").

What a resume should do: ignore the old page. Open a fresh tab at a known URL, close every other tab,
verify the account header and the persona, and re-run the step from its start. This is a design rule, not a
measurement.

Engine hygiene: the resident Stagehand extension keeps tripping `isAutomatedWithCDP` until uninstalled or
the browser restarts (D6, `CONSISTENCY.md` C-13). Maria's session runs in that browser. Her typing arrives as
CDP input events from the viewer. `docs/identity/identity-and-proxies.md` §2.2 already says "Only a human doing the
action is clean"; a person in the viewer is a **human driving an automated browser**, not "their own
session". The docs use the two interchangeably (`social-channels.md` §6 "in their own session or in the
viewer") (G12-10).

## 6. Should she be able to watch without taking over?

Many reasons to look do not need control: the client wants to see the agent post; the owner is debugging;
Maria wants to confirm a step before approving. Today the only way in is takeover, which stops the agent.

Steel documents a read-only mode: `interactive=false` makes the view "read-only, ideal for watch-only
monitoring" (`https://docs.steel.dev/overview/sessions-api/embed-sessions/live-sessions.md`, headful
and headless parameters). The node agent already allows the `interactive` parameter through its route
allow-list (`steel-profile.md` §9.3). A **watch ticket** needs no lease, so it cannot preempt anyone.

Cautions, all unverified:

- `interactive=false` is a URL parameter. Whether the cast WebSocket honours it server-side is unknown, and
  the route "ignores the session id" and has no authentication (`steel.md` §7.1). The broker must force the
  parameter and drop client input frames itself. **To measure.**
- A watch ticket shows everything on screen: DMs, notifications, personal data. The same operator
  authentication as takeover applies; watch tickets are per tenant (RLS, §6.6).
- Streaming costs CPU on the node (the screencast is a JPEG stream; headful WebRTC is not measured on OSS,
  `steel.md` §7.1).
- **Browserbase-homed identities cannot offer this.** Live View read-only is the embedder adding
  `pointer-events: none` to the iframe (`https://docs.browserbase.com/platform/browser/observability/session-live-view.md`),
  which only the embedding page enforces. The Live View URL is a bearer capability. Fleetd also cannot cut
  a Live View holder without `REQUEST_RELEASE`, which ends the agent's session too (ARCHITECTURE §3.5,
  `docs/engines/browserbase.md` §2.7). Offer screenshots, not the URL.

## 9. Dependencies

AQ-1 (how operators authenticate) blocks every human session. M1 G1.5 (viewer handles real input) and G2.6
(takeover) are the existing gates. The new behaviours above need M2 (lease, node agent), M4 (ledger,
manifests, connectors for the diff in G12-5) and the console UX, in that order.
