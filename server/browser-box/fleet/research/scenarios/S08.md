# S08. A node crashes in the middle of a browser-channel post

Stress test, group 3. Read against the design as written on 2026-10-10. **Nothing described here is built.**
Every step below is a walk through the target, not a run.

**Verdict: breaks.** The pattern is right: an intent row before the click, a read-back after, a hold when the
outcome is unknown, never a blind retry (DEC D13, ARCH §3.6). As written, two holes let a second post through.
The ledger key includes the job's task id, so a re-created job gets a new key (S08-1). And the hold that blocks new
work is set after the lease expires, not with it, so a queued job can slip into the gap (S08-2). Both are fixable
in the spec with no new capability. Until they are fixed, the claim "no double post" is not supported by the
documents. The rest of the table is about making the recovery usable: fencing across a partition (S08-3), the
journal that must outlive the node (S08-4), what a negative read-back may mean (S08-5), and what the owner sees
(S08-7).

## What the walk assumes

- Client "Acme", identity `acme-fb`, a Facebook Group post. Groups have no API (SC §5, §6), so this is the narrow
  browser set: the client's written risk acceptance is on file, `channel_policy.browser_allowed` includes `post`,
  `browser_hitl` is `per_action`, the click is `agent_clicks` (the ARCH §4.7 default).
- Defaults hold: Q-01 API-first, Q-13 one client per node, M1 and M4 gates passed. None of it exists.
- The post is an effect: kind `post`, target the group, content from a human-approved draft (ARCH §4.7, §5.3
  `publish`). It is not from page text.
- "Crash" means the node (droplet, node agent, containers) is gone or unreachable. Two variants are walked: the
  node is **dead**, and the node is **partitioned** (still running, unreachable from fleetd).
- Lease TTL, renew interval, grace window and journal interval are not specified anywhere. They are shown as
  `TTL`, `grace`, `J`.

| Window | `effects` row | Platform | The design's conclusion | Note |
|---|---|---|---|---|
| C0: before step 8 | none; approval unconsumed (if consumed at intent) | Nothing posted | Job interrupted. Rerun is safe because nothing was recorded. | Safe only if nothing else was consumed (S08-1). |
| C1: after step 8, before the click leaves | `intent` | Nothing posted | Becomes `uncertain` at lease expiry. | Correct but conservative. The owner must check by hand. |
| C2: click sent, platform answer unknown | `intent` | Maybe posted | `uncertain` | Truly unknown. |
| C3: platform accepted, read-back not run | `intent` | Posted | `uncertain`; the reconciler's read-only job should find it. | Depends on the read-back (S08-5, S08-6). |
| C4: read-back succeeded in the node, commit not written | `intent` | Posted | Same as C3. | The receipt is lost with the node. |

### The partitioned variant

The node is alive, its Chromium is running and holds the post's composer. fleetd cannot reach it. Steps 11 and 12
happen on fleetd's side. The old executor can still be mid-click. The new node wakes under T+1 and reads back
"absent" because the old click lands a moment later. ARCH §4.10 answers this with self-fencing: "the node agent
kills the identity's containers if renewals fail for a TTL". That is the right idea. The numbers and the order are
missing (S08-3).

### What stops a second post, layer by layer

| Layer | Mechanism | Works when | Hole |
|---|---|---|---|
| 1 | `effects.effect_key` unique; `ON CONFLICT DO NOTHING` (ARCH §3.6) | The repeat has the same key. | The key is `H(identity_id, task_id, kind, target, content_hash)`. A re-created job or a replacement identity changes it (S08-1, S07-5). |
| 2 | `jobs.idempotency_key` unique per token and tool (ARCH §3.9) | The same agent resends the same key. | A new key from the agent. A scheduler-created job has no token, so the rule does not apply (S08-1). |
| 3 | Identity hold refuses `work` (ARCH §3.5) | The hold exists. | Set after expiry by another process (S08-2). |
| 4 | Approval is single use (`consumed_by_effect_id`) | Consumption is atomic with the intent row. | Not stated. At commit, a crash leaves it unconsumed. `per_item_cap` has the same question (S08-1). |
| 5 | Fencing token on every command (ARCH §3.5, §4.10) | The next command comes after the higher token. | Does not stop a click already handed to CDP, and does not stop a partitioned node (S08-3). |
| 6 | Read-back and reconciliation | The post can be found. | Feeds index late; DM requests land elsewhere (ARCH §4.7 step 7); a group may hold a post in a queue (inference; the research does not cover it). A false "absent" followed by a retry is a double post (S08-5). |

## What the design gets right

- **Intent before the click.** The intent row is committed to the database first (ARCH §3.6, gate G step 6). This
  is the property that lets recovery know anything.
- **Nothing is retried on a guess.** An existing `intent` or `uncertain` row answers `outcome_uncertain` and does
  nothing. No error code tells a caller to retry under a new key (ARCH §5.5).
- **The hold has a purpose.** `reconcile`, `reauth` and `maintenance` can take the lease while held, so reconcile
  does not deadlock (ARCH §3.5, §9.1 item 5).
- **The token is checked by whoever acts.** Node agent and executor refuse stale tokens, and the node agent keeps
  the highest token on its disk across a restart (SP §9.1).
- **The agent's instructions are right.** `fleet-social` and `fleet-router` say: do not repeat, tell the owner,
  "sent, not verified" is an honest report.
- **It is honest about the receipt.** Browser read-back is called a hypothesis in DEC D13, ARCH §3.6 and SC §8.

## Checks against the charter and platform rules

| Rule | Result |
|---|---|
| CH invariant 2 (one writer, fencing checked by whoever acts) | Met for commands. Not met for an in-flight click or a partitioned node (S08-3). |
| CH invariant 5 (journaled, verified, never blindly retried) | The pattern is met. The key and the hold race let a retry through in two paths (S08-1, S08-2). |
| CH invariant 6 (API first; browser only for the narrow set, human-approved, risk accepted) | Met for the walk. ARCH §8.4 and SC §6.1 disagree on whether a manifest may authorize a browser post (S08-9). |
| CH invariant 8 (client isolation) | Reconcile wakes under the same tenant's rules. One-client-per-node holds for a replacement node. |
| CH "agents never retry an uncertain effect" | Holds in the agent skills. |
| Platform rules | Facebook Groups: browser-only, ToS-exposed (SC §6). A human approving does not make automated UI driving permitted. The strongest option is `human_clicks` (SC §6.1). |

## Where DECISIONS looks wrong or silent

- **D13** says "an intent row committed before the click". That is true. It does not say how the key is made.
  A key that includes the job's task id defeats the pattern. State the key rule in DEC D13 (S08-1).
- **D12** says an identity with a held or uncertain effect is blocked until reconciled. As specified, it is
  blocked only after the reconciler has run (S08-2).
- **D2** and **D13** do not decide whether a manifest may authorize a browser-channel post (S08-9).
- **D4** gives the safe release order and the crash note "the lease expires". It does not give TTL, interval or
  fence (S08-3).

## Not checked

- How often a node dies mid-effect. No soak test exists (SCV missed issue 3). The load on humans scales with the
  rate of `uncertain` rows, which DEC D13 says is set by the read-back false-negative rate. Nobody has measured
  either.
- Whether a Facebook Group's feed shows a just-posted item to the poster inside any grace window, and whether
  pending posts are visible to the poster. Only M6a can measure it.
- Whether Chromium restores tabs or resubmits anything after a droplet reboot with Docker restart policies. The
  node agent aborts containers without a lease (SP §8.3); the policy should be `no`.
- Real composer behaviour for `Input.insertText` on Lexical and Draft.js editors (M1).
