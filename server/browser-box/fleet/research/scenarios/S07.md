# S07. An identity's static proxy IP dies or its exit IP changes

Stress test, group 3. Read against the design as written on 2026-10-10. **Nothing described here is built.**
Every step below is a walk through the target, not a run.

**Verdict: handled with gaps.** Detection is well specified. Wake refuses on a wrong IP, the forwarder fails
closed, and nothing reconnects through another path. What is missing is everything after the alarm: how a hold
is cleared (S07-3), what "replace" means for the data keyed to the old identity (S07-5), what the client is told
(S07-8), and what happens when a whole vendor fails at once (S07-9). Two defects are sharper than the rest. A
proxy hold also stops the API channel, which never uses the proxy (S07-4). And a mid-session swap leaks a
bounded but unspecified number of requests, which the gate calls "zero" (S07-11). Gaps are in the table at the end.

## What the walk assumes

- Client "Acme" is a tenant. Identity `acme-fb` is kind `account`, home `steel-oss`, one dedicated static ISP IP
  (ARCH §3.3). It has both channels: an API connection for the Facebook Page, and the browser channel for one
  Facebook Group (the no-API set, SC §6), with a risk acceptance on file and `browser_hitl: per_action`.
- Defaults hold: Q-01 API-first, Q-06 every cap is $0 until Justin names one, Q-13 one client per node, Q-12 a
  droplet exists, M1 gates have passed. None of that exists yet.
- The vendor sells "static ISP, dedicated". The research does not say whether the exit IP is the proxy host
  address or sits behind a gateway, how the vendor authenticates, or what the vendor's replacement policy is
  (ID §3.7: "same IP on renewal? replacement policy? no silent rotation?" is a question to ask, not an answer).
  Three cases are walked: **A** the IP is gone or changed when the identity wakes; **B** it changes mid-session;
  **C** the owner replaces it.

## What the design gets right

- **The check is before the browser.** W9 runs the echo before any session is created. "No browser ever runs on a
  wrong IP" is true at wake (ARCH §4.1 W9, ID §2.3).
- **There is no fallback.** The container's only route out is the forwarder, and the forwarder never goes direct
  (CH invariant 9, ARCH §6.3). A dead upstream makes Steel fail closed (hands-on, ENG-S §6).
- **Replacement is not silent.** ID §3.7 forbids reconnecting through another path and forbids a new IP as an
  answer to a platform restriction. A new IP is a new login, and the platform sees it as one.
- **The vetting rule applies again.** A replacement IP goes through the same six checks (ID §3.3). The NetNut
  lesson, that a vendor name does not tell provenance, is built in (APV AP-7).
- **IPRoyal's silent swap is named** and `_killswitch-1` is required for any rotating product (DEC D10).

## Gaps

Severity: blocker = the scenario cannot finish safely as designed. major = it can finish but unsafely, or only by
guessing. minor = wording, ownership or a missing detail.

| S07-1 | major | architecture | **A transient outage and an incident share one path.** SP §6.2 rule 3 treats "upstream down, 407, timeout" the same as an exit-IP change. ## Where DECISIONS looks wrong or silent

- **D3** is right about continuity and wrong in its wording about identity rows (S07-6). Fixing the wording does
  not weaken the rule: a new IP is still a new device and a fresh login.
- **D10** fixes the forwarder's behaviour on an exit-IP change and the vetting rule for a new IP. It is silent on
  vendor concentration, replacement ownership and spares (S07-9).
- **D12** says an identity with a held or uncertain effect is blocked. It does not say that a hold unrelated to an
  effect should not stop the API channel (S07-4).
- **D14 and ID §3.7** say "tell the client first". Nothing says how (S07-8).

## Not checked

- Whether a static ISP exit IP is the proxy host's address or sits behind a gateway; how the vendor authenticates;
  whether a vendor ever swaps a dedicated IP on its own; the vendor's replacement terms. The corpus has none of it.
  Ask in the provenance statement (ID §3.3 check 5).
- How Meta, TikTok or LinkedIn react to a cookie jar that moves to a new IP. Nothing was run on those sites (CON §7;
  ID §6 "never measured"). Only M6a can measure it.
- The forwarder's real check interval and whether Chromium's connection pooling lets a request through after the
  block. M1 G1.2.
- The failure rate of IPs at fleet size. No figure exists. S07-9 is written as a formula problem, not a rate.
