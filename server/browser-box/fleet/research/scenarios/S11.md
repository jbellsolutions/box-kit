# S11: a Hermes profile asks the tool something vague or risky

Role: scenario stress-tester, group 4. Walked against `fleet/DECISIONS.md`, `fleet/ARCHITECTURE.md`,
`fleet/CHARTER.md`, `fleet/SOUL.md`, `fleet/MILESTONES.md`, `fleet/docs/**`, `fleet/hermes/**`. Nothing is
built. "What happens" means "what the drafted design would do".

**Verdict: breaks** (charter promise "red lines are refused in code, not by prompt" has no implementing
mechanism for the read side or for approvals). Per request:

| Request | Verdict | Why |
|---|---|---|
| "Grow my client's TikTok fast" | handled-with-gaps | Vague goal, but every concrete piece it decomposes into either has an allowed route or is refused. Gaps: no guidance for vague goals, no TikTok channel until approvals exist, no owner notice for a refused ask. |
| "DM everyone who liked our post" | breaks | Nothing checks that a recipient wrote first or opted in. A red-line DM request becomes `needs_approval`, which a human can approve. The "everyone who liked" list cannot be built without scraping. |
| "Scrape LinkedIn for leads" | breaks | Refused only in skill prose. No host policy, no code refusal. It stops only because LinkedIn shows a login wall. |

Read this first: **fleetd never sees these sentences.** It sees tool calls. So there are two refusal
layers, and they behave very differently.

| Layer | What it is | Strength |
|---|---|---|
| Hermes side | `SOUL.md` fleet-operator section, `fleet-router`, `fleet-social`, `fleet-leadgen` | Prompt. Can be missed, misread, overridden by a hostile page, or absent (the Jev trial gets only a 6,000-character guide). |
| fleetd | Token scope, identity state, channel router (`publish`, `run`), gate G (`act`, `task`), manifests and approvals, governor, connector capabilities | Code. But it is built around **effects**. It has no component that decides "this kind of effect must never happen, whoever approves" and none that governs **reads**. |

## 1. Where each red line is enforced in the drafted design

This is the table the charter implies exists. It does not exist in the design. I built it by walking
`ARCHITECTURE.md` for each red line in `CHARTER.md` ("Red lines": "The fleet refuses these in code, not by
prompt").

| Red line | Mechanism in ARCHITECTURE | What actually stops a confused or hostile caller | Strength |
|---|---|---|---|
| Cold / outbound DM | `publish kind=dm` needs scope `dm` plus a manifest item or approval (§3.4, §4.6, gate G). `target` is a free string. | A human approver. For Meta and TikTok, the platform's own messaging rules (SP-10: Instagram "only after an Instagram user has sent ... a message"; TikTok "prohibited from initiating a conversation"). For X, only X's written rule against bulk or automated unsolicited DMs; whether its API also refuses is **not established by the research**. | weak |
| Automated likes, follows, engagement | No tool for it. `follow` is an effect `kind` in the ledger (§3.6). `act` on a Like button is "effect-like": `needs_approval`. A released procedure may declare `follow`. | A human approver. A procedure author. | weak |
| Scraping platforms for lead data or people | `extract` and `task` in `read_only` mode: allow-list = navigate, scroll, find, extract, links, search boxes (§4.3 gate G). The guard denies private ranges and fleet hosts only (§2.3, §6.4). | Nothing, until a login wall appears. | none |
| Any agent browser on x.com | No host policy anywhere in §2-§6. | `fleet-router` prose. | none |
| Any LinkedIn browser automation | **Contradicted.** §8.3 lists "LinkedIn connection requests and DMs" in `browser_allowed`; the `fleet-social` skill §2 repeats it; charter and `social-channels.md` §6 say the fleet runs no LinkedIn browser. | Nothing consistent. | none |
| Identical posts across client accounts | "A duplicate-content check runs before every publish" appears in the charter and `social-channels.md` §2.1. It is **not in ARCHITECTURE** (no table, no step in §4.6/§4.7). | Nothing. | none |
| AI auto-replies on X | `publish` rule: AI-drafted X replies need per-action approval (§5.3 tool 9). | A human approver. | medium |

Two consequences. First, G4.6 in `MILESTONES.md` (the automated refusal suite, "100% refused with
`scope_denied`") tests a mechanism that ARCHITECTURE never specifies. Second, `extract`, `task` and `act`
are first listed in M3 (`MILESTONES.md` §2.3) and the refusal suite is in M4. For one milestone, a profile
holds read tools with no red-line gate.

## 2. Request A: "grow my client's TikTok fast"

### A1. The profile decides what the sentence means (Hermes side)

`fleet-router` begins: call `fleet_status`. It then offers a table of **needs** ("Post, reply, comment or
message", "Data from a page", ...). There is no row for a **goal**, and no instruction to ask what "grow"
and "fast" mean, which platform account, or what the client's limits are. The profile improvises. The
only rule that applies is SOUL: "If a goal cannot be met safely, say so and offer what I can do instead"
and "Slower than the limits".

"Grow fast" splits into pieces. Each piece lands somewhere different:

| Piece | Allowed? | Route in the design |
|---|---|---|
| Post original content on a steady schedule | Yes | Accounts API through `publish`, from an approved manifest. TikTok caps the endpoint at 15 posts a day per account (`docs/channels/social-channels.md` §3.2, official-docs). |
| Reply to comments on the client's own posts | Yes | `publish kind=reply`, API, approved template or draft |
| Reply to DMs that users sent first | Yes, with limits | Business Messaging API: open beta, **not in EEA/CH/UK**, needs reviews |
| Read performance numbers | Yes | Analytics through the API |
| Likes, follows, unfollows, comment-spam, engagement pods, bought followers | **Never** | Red line (automated engagement) |
| Cold DMs | **Never** | Red line; TikTok: "prohibited from initiating a conversation" |
| Reposting downloaded TikTok content | **Never** | Red line (Accounts API prohibited use) |
| Ads, boosts, anything with money | Human only | Social-channels §7 HITL point 7 |
| Research what is trending | Not allowed through the fleet | TikTok bans automated extraction (D2). No charter line names trend research, so the design is silent (gap G11-9). |

### A2. What the fleet says when the profile checks (tools: `fleet_status`, `identity_status`)

Under default answers (Q-06: nothing applied for, nothing approved), the TikTok connector is **not ready**
(`MILESTONES.md` G4A.5: a platform is ready only in the "approved" state; charter invariant 6: "a channel
without its approval is not offered"). `identity_status` shows `channels.api: unavailable`,
`channels.browser: not_allowed` (no risk acceptance). If no browser identity exists for TikTok either,
there is nothing to wake. `publish` answers `channel_unavailable`.

So the honest first answer is: *the fleet cannot post to this TikTok account yet, and the reason is an
approval Justin has not applied for.* That is a **gap, not a refusal**, and Justin's rule applies: say what
is missing and what is being done. The skills do not say who does what. The only "owner" channel is
`feedback`, and the skills do not tell the profile to use it for this.

### A3. What the profile can still do alone

Hermes-only work, outside the fleet: a content calendar, scripts and captions in the client's voice
(SOUL: if there are no samples of their voice, say so and ask), a draft manifest for a human to approve.
These produce `draft` approvals and Obsidian notes. Nothing ships.

### A4. What the profile must say, and who is told

Proposed reply shape (not in the skills today; gap G11-6):

1. What I can do: scheduled original posts from approved drafts, comment replies, analytics, once TikTok
   access is approved; drafts today.
2. What I will not do, once, with the reason: automated likes and follows, cold DMs, reposting other
   people's videos, anything meant to look like organic growth that is not.
3. What needs a person: TikTok access approval (Justin), post approval, any ad spend.
4. What "fast" can mean: more steady output inside the platform limits. No platform publishes a safe
   cadence, so I will not quote one (`fleet-social` §4).

**Who is told.** Charter escalation: "a client asks for something on the red-line list" means stop and
ask the owner. A refused request is not a job, so `job list` has no row, so the daily note (built from
`job list`) will not show it. Only a `feedback` call or an Obsidian note by the profile records it, and no
skill says to write either (G11-6).

**Verdict A: handled-with-gaps.**

## 3. Request B: "DM everyone who liked our post"

### B1. Hermes side

`fleet-social` §5 red line: "Cold or outbound DMs to anyone who has not written first or clearly asked or
opted in." `fleet-social` §6: reply "only on the API channel, inside the platform's window". A careful
profile refuses once and offers alternatives. The design relies on that. Now the careless or hijacked
profile, call by call.

### B2. Building the list of likers

The profile needs the people who liked. There is no fleet tool for it. Options it has:

1. `extract` or `task` on the platform's website through an `account` identity, opening the likers dialog.
   Gate G `read_only` permits navigating, scrolling and extracting. Nothing stops it. This is scraping
   people from a platform: red line, and the terms of each platform bar it (`docs/playbooks/lead-gen.md`
   §1.1 and §1.4; `research/verification/social-platforms.md` SP-11). **No code refuses.**
2. A platform API. The research did not find or read any API that returns the people who liked a post,
   and the connector interface (§2.6) has no such method, so the profile cannot call one through the fleet.
   If one exists, using platform APIs to profile users is a red line (SP-11).
3. The client's person copies names into chat. The profile now holds a list of people who never contacted
   the account.

The chain therefore fails at the **read**, but only by luck. It is not designed to stop there.

### B3. Sending

Per recipient: `publish{identity, platform, kind:"dm", target:"@someone", draft:{text}, idempotency_key}`.

| Token holds | What the design does | Result |
|---|---|---|
| `draft` only | A draft with no item or approval **creates an approval request** and answers `needs_approval` (§5.3 tool 9) | One approval per recipient. 500 likers = 500 pending approvals and 500 notifier alerts. |
| `dm` and an approved manifest with `dm_template` + `target_rule` | Campaign-level authorisation (§3.7, §4.11). Items run **without a Hermes call** inside the window and caps. | The manifest is a human's yes to a *rule*. If the rule is "people who liked post 123", nothing in §3.7 or §4.6 rejects it. |
| `dm` and a one-off approval | The approver clicks Approve on "DM @someone: <text>" | The effect proceeds. |

What stops it, per platform:

- **Meta (Messenger, Instagram):** the platform refuses a first message. The API answers 4xx, which the
  ledger treats as `failed_clean` (§4.6 step 6). So no DM is sent. But the fleet sent N calls that it
  knew, or should have known, were prohibited, and the platform sees an app repeatedly attempting
  unsolicited messages (inference, not measured).
- **TikTok:** same, "prohibited from initiating a conversation" (SP-10).
- **X:** X's rule bars "unsolicited Direct Messages in a bulk or automated manner" and allows a DM when the
  recipient "requested or ... clearly indicated an intent ... to be contacted" (SP-10, quoted from X). The
  research does not say whether the API itself refuses a first message. `social-channels.md` §5 X cell
  says "recipient asked for contact or **clearly showed intent**", which a lenient approver could read to
  cover a like. **Nothing but the human approver is specified** (G11-3, G11-10).
- **LinkedIn:** no API; messages are always a person's action.

### B4. The part the design never specifies: how does the fleet know a recipient wrote first?

- There is **no tool that gives the profile an inbound message or thread.** The 14 tools in §5.3 contain
  no inbox read. `fleet-social` §6 tells the profile to reply "through `publish` with `kind: reply`", but
  it has no thread reference unless a human pastes one.
- `publish` takes `target?: string`. There is no `thread_ref`, `consent_ref` or `inbound_event_id`.
- The connector interface has `reply(thread, text)` (§2.6), so *the connector* thinks in threads. The
  public tool does not expose it.
- `docs/channels/social-channels.md` §2.1 and `MILESTONES.md` §4.6.1/§4.6.3 describe webhook receivers,
  a per-conversation window tracker, a consent ledger and an opt-out ledger. **ARCHITECTURE §2.1 and §3
  have none of them.** A builder following ARCHITECTURE would not build the data that recipient
  eligibility needs.

Without that data, the "wrote first" rule is a sentence, not a check.

### B5. Refusal code

A red-line request should end in an answer the caller cannot "fix":

- `needs_approval` (current result for a draft DM, and for `act` on a Like button) invites approval.
- `scope_denied` (MILESTONES G4.6, social-channels §7) means "the token lacks the scope" (§5.5; the skill:
  "use a tool you are scoped for"). It invites granting the scope.
- No code means "no scope, approval or manifest can unlock this" (G11-2).

Also: a hostile or buggy loop of 500 `publish` calls each opens an approval. There is no cap on pending
approvals per token and no check for near-identical text across targets (the mass-DM pattern) (G11-5).

### B6. What the profile should offer instead (all from the research; nothing invented)

- **Reply to people who commented or messaged.** API, inside the platform window, approved templates or
  drafts. Meta's private reply to a comment is allowed for 7 days (`social-channels.md` §3.1.3).
- **Make the next DM legitimate.** A post or story that invites people to message a keyword, which gives
  prior contact and consent. A consent-based channel (Lead Ads, opt-in DM capture, LinkedIn Lead Gen Forms,
  TikTok instant forms) is a first-class option **pending Q-14**; the research on how to build them is
  **unresearched** (`docs/playbooks/lead-gen.md` §2.4). Ad spend is human-only.
- **A person messages individuals** from the platform's own app, in their own session. The fleet is not
  involved.
- **Aggregate analytics** of the post's engagement, not a list of people.

**Verdict B: breaks.** Three holes: no recipient-eligibility check, no inbound/consent data, no code that
cannot be approved away.

## 4. Request C: "scrape LinkedIn for leads"

### C1. Hermes side

Three skills say no: `fleet-router` ("Never scrape social platforms for people"), `fleet-leadgen` ("Not
allowed: logging in to a social platform to collect people, or scraping profiles from ... LinkedIn"), and
the charter red line ("Scraping platforms for lead data"; "any LinkedIn action by browser automation").
A careful profile refuses once and offers the open-web cascade.

### C2. What the fleet does if the profile tries anyway

`extract{identity: <research identity>, url: "https://www.linkedin.com/...", via: "auto"}`:

1. §4.4 step 2: for a `research` identity, **L0 plain HTTP** through the identity's forwarder. No host
   policy blocks `linkedin.com`. The fetch goes out. LinkedIn returns an auth wall or a thin page.
2. "Escalate on the goal being unmet": `via: browser`, wake a browser, navigate. The page shows a login
   wall. Blocker `login_wall` -> the identity pauses (`needs_reauth`). Research identities never log in, so
   the run ends. The agent is told to stop.
3. `task` on a research identity with a goal like "find people at Acme on LinkedIn" is the same, except it
   may wander through public Google results first (lead-gen §3.10 says scraping search results is not
   allowed; no code enforces it).

Net: the run stops because **LinkedIn** has a login wall, after one or more requests left from the research
identity's static IP to a site whose terms forbid them (LinkedIn User Agreement §8.2, `social-channels.md`
§3.3). It is not stopped by the fleet. The charter says "in code, not by prompt." Here it is by the target
site's behaviour (G11-4).

### C3. Ways around the fleet that the fleet cannot see

The red lines bind the fleet. They do not bind the rest of the profile:

- The profile may hold other MCP servers. `fleet-leadgen` says "not any other lookup API or MCP, even one
  connected to your profile". That is a prompt. The provisioner sets `agent.disabled_toolsets: [browser]`
  (ARCHITECTURE H1) and nothing more.
- Justin's own agent stack names browser-use, Orgo and Composio as the enrichment tools; Composio
  connectors "may already wrap these official APIs" and carry no fleet gate (`social-channels.md` §2.5,
  `MILESTONES.md` N-9, "not researched"). A profile that keeps a Composio social toolkit or a LinkedIn lead
  MCP can do request B or C with zero fleet involvement.

The fleet cannot enforce this from the inside. It can only set what the provisioner writes into each fleet
profile and report on it (G11-8).

### C4. What the profile should offer instead

All from `docs/playbooks/lead-gen.md`:

- **Owner-supplied list of company domains** -> the open-web cascade on the companies' own sites (tier 0
  fetch, tier 1 Stagehand `extract`, tier 2 `task`), robots.txt first, role-based contacts, source URL and
  time with every datum, notes in `Leads/<company-slug>.md`.
- **Consent-based channels** the client runs, pending Q-14 (unresearched).
- **A person uses LinkedIn** in their own session; the agent drafts, the person sends. No LinkedIn browser
  in the fleet.
- **Discovery** ("find companies that match X") is an **open gap**: lead-gen §3.10 says the research does
  not cover it and the fix is a research task owned by the playbook author. Until that table of approved
  sources exists, discovery is owner-supplied lists only. This is the capability gap Justin's rule
  covers: say it is missing, say what is being done (the research task), and do not fill it with a paid
  service (Clay, Apollo, Hunter, ZoomInfo, Ocean.io).

**Verdict C: breaks.**
