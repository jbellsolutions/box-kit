## Read this first: Steel Cloud is not the open-source `steel-browser`

The docs at docs.steel.dev are written for **Steel Cloud** (`api.steel.dev`, `app.steel.dev`). Our target is the self-hosted OSS `steel-browser` (`https://github.com/steel-dev/steel-browser/tree/1131a02`). They are different products sharing a name and a thin API subset. Every row below carries a marker:

- **CLOUD** = Steel Cloud only. Do not assume it exists on a self-hosted box.
- **SELF** = present in the self-hosted OSS repo.
- **BOTH** = present in both (shape may differ).

Provenance tags follow BRIEF.md: `official-docs`, `source-code` (pinned commit), `hands-on` (ran today), `vendor-claim` (marketing/pricing/blog), `third-party`, `unverified`.

### Where the docs and the source disagree (source wins)

1. `https://docs.steel.dev/overview/self-hosting/steel-local-vs-steel-cloud.md` says Files are "Not supported" in Steel Local. The self-hosted routes and both SELF specs expose `/v1/sessions/{id}/files*`. (`source-code` + `hands-on` win.)
2. `https://docs.steel.dev/overview/self-hosting/docker.md` health check is `/api/health` and says Chrome 128.0.6613.119. At 1131a02 the health route is `/v1/health` (returned 200 on the running image) and `api/Dockerfile` installs unpinned Debian `chromium`. The doc is stale.
3. The same Local-vs-Cloud page says Steel Local concurrency is 1, stealth is "Limited", CAPTCHA solving "None", credentials "Not supported". Consistent with the SELF spec (no captcha or credentials endpoints). Concurrency 1 is corroborated by `source-code`: the SELF spec describes itself as "controlling a single instance of Steel Browser" (`info.description`), and the README says `POST /v1/sessions` relaunches the one browser and resets its state. One Steel Local container therefore means one live browser; a fleet needs one container per concurrent browser (not yet measured, `unverified`).
4. `https://docs.steel.dev/overview/stealth/proxies.md` uses old plan names (Hobby / Developer / Pro). `https://docs.steel.dev/overview/pricinglimits.md` (last edit June 30th, 2026 per the page) uses Launch / Scale / Enterprise.
5. `https://docs.steel.dev/llms.txt` agent instructions say "Do NOT use `session.websocketUrl` directly" and to build `wss://connect.steel.dev?apiKey=..&sessionId=..`. The integration pages (Stagehand, Browser Use) use `${session.websocketUrl}&apiKey=...`. Both appear in the docs.
6. `https://docs.steel.dev/integrations/hermes-agent.md` calls the Hermes integration "pending". A standalone plugin repo exists (`https://github.com/steel-dev/hermes-steel/tree/d8a1e39`) and the steel.dev blog has two Hermes posts (`https://steel.dev/llms-full.txt`). The plugin README says self-hosted works via `STEEL_BASE_URL`.

### Empty or missing pages in the official docs

Four self-hosting pages are title-only stubs, so **the docs say nothing** about them: `https://docs.steel.dev/overview/self-hosting/{clustering,extensions,profiles,webrtc}.md`. For self-hosted profiles, the only real information is the `userDataDir` / `persist` request fields, `CHROME_USER_DATA_DIR`, and the `.cache` volume note in `https://docs.steel.dev/overview/self-hosting/docker.md`. `docs/overview/self-hosting/render` is listed in the sitemap but is only an external link (`isLink: true` in the docs repo; the site serves an empty SPA shell), so it was not captured. There is no dedicated "stealth" or "fingerprint" page anywhere in the docs.
