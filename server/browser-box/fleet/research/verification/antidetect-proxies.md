# Verification: `dossiers/antidetect-proxies.md`

Verifier: adversarial verifier (not the dossier's author). Date: 2026-10-10. Spend: **$0** (no LLM or OpenRouter call was needed).
Nothing hands-on: no Docker command of any kind, no browser launch, no hermes CLI. Containers left running: **none** (none created).

**How I checked (and how that differs from the author)**
- **Stagehand.** I re-read the installed `@browserbasehq/stagehand@4.2.0` `dist/` and its extension.
- **Steel.** I re-read `steel-browser@1131a02`. For the GPU string I grepped the *original* obfuscated `fingerprint.js`, not the author's decoded copy.
- **Browser-Use.** I diffed the `browser-use@c75e847` clone against the installed 0.13.11 package. Every cited file is byte-identical, so the source claims apply to the version that was measured.
- **Upstream Chromium.** The author did not use this route. I read Chromium's DevTools source in the `chromium/chromium` GitHub mirror at release tags `146.0.7680.177`, `147.0.7727.0`, `148.0.7778.0`, `149.0.7827.0`, `151.0.7922.0` and `152.0.7977.82`, plus the commit history.
- **Raw spike outputs.** I re-parsed every raw JSON file and reconstructed the run order from file mtimes (EDT) in `<scratch>/spikes/antidetect-proxies/`.
- **Web pages.** I re-fetched the primary pages on 2026-10-10. Vendor pricing pages are `vendor-claim`.

**What the Impact column means:** what my verdict does to the fleet design. `none` means the claim stands as written.

**Sample sizes behind the hands-on claims:**
- Every DABI (deviceandbrowserinfo) cell is **n=1**.
- The Stagehand "resident leak" was observed once, about 40 s after `close()`.
- Seed stability: n=2 runs for one seed, n=1 for a second seed.
- Steel `hasInconsistentWorkerValues`: n=2 (runs D and E; A and B had no DABI read).
- The Steel container image (pulled 2026-09-16) is older than the pinned source (2026-10-06). `cdp.service.ts` changed in between (#366, #327, #374).

1. **The Stagehand-on-vendor-kernel question has a version answer: Chromium ≥149.**
   - Upstream commit `dddf05b0e6` removed the pipe and flag gate in M149. Chromium 147-148 has `getExtensions` but keeps it gated; ≤146 does not have it.
   - So Stagehand 4.2.0 `connect` can never attach to a ≤148 kernel, and the per-vendor conformance test can start with the kernel's major version.
   - CloakBrowser Pro (150-154) probably qualifies. Older vendor kernels need Stagehand v3.7.3 (`v3-latest`) or Browser-Use.
2. **Fourth Stagehand prerequisite: `--remote-allow-origins`.**
   - The extension's service worker dials CDP from origin `chrome-extension://<id>`, and Chromium returns 403 unless that origin is allowed.
   - Vendor launchers (Multilogin, Kameleo, DICloak) may not set the flag, and vendor CDP proxies such as Kameleo's `/playwright/{id}` may handle the Origin header in their own way.
   - Allowing `*` also lets any local origin open CDP if it learns the browser GUID. This is the security cost of the workaround.
3. **`--lang` does not work on Linux** (Chromium's own switch comment). The persona-application recipe in §3, §4 and the wake sequence must use `LANG`/`LANGUAGE` plus `--accept-lang` or the `intl.accept_languages` pref. Stagehand's `locale` option relies on `--lang`.
4. **Steel ignores `userDataDir`.**
   - The dossier's own §4 session body still sends it.
   - Runs A ("profA") and B ("profB") were not separate profiles.
   - Sibling dossiers caught this; this one did not.
5. **CloakBrowser's Windows persona on Linux needs Microsoft-proprietary Windows fonts.** Its README calls a Windows persona without them "itself a bot tell". The spike did not install them, so the "clean" CloakBrowser results never exercised font fingerprinting. Shipping those fonts in fleet images is also a licensing question.
6. **CloakBrowser BINARY-LICENSE v1.3:**
   - an OEM/SaaS licence is required when third-party customers get "control over" the browser, which client logins through the live viewer may trigger;
   - the latest major build needs a paid subscription;
   - the binary phones home for licence and concurrency checks.
   
   This weakens Verdict 2(b)'s framing of CloakBrowser as an "OSS-compatible" route.
7. **Spoofed GPU over software rendering (inference).**
   - Kameleo's Docker docs: "Without a mounted GPU, the container falls back to software rendering".
   - On GPU-less droplets, vendor and patched personas claim an NVIDIA D3D11 GPU while rendering in software. Castle-style "red pills" (rendering timing and capability) can catch that.
   - So the proposed canary is not "Linux persona vs genuine Windows". Both arms run on software rendering.
8. **IPRoyal sticky sessions silently swap the IP by default.** The docs say "the system silently assigns a replacement" unless `_killswitch-1` is set, which returns HTTP 410 instead. This belongs in the "exit-IP change = incident" design for any rotating provider.
9. **The action re-test needs a behaviour test.** The DABI page advertises a separate test that "detects CDP mouse leak" (text inside `raw/runD.json`). Both engines click with CDP `Input.dispatchMouseEvent` (inference), and CloakBrowser claims "CDP input behavior mimicking". The click/type/scroll re-test should use that page, not only `are_you_a_bot`.
10. **`browser_use/integrations/anthropic` sends `Runtime.enable` and `Log.enable`.** It is a Browser-Use path that trips the CDP check, missing from the dossier's list.
11. **Statistical weakness.**
