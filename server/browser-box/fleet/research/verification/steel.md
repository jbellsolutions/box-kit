# Verification: Steel dossier (adversarial pass)

Date: 2026-10-10. Target: `fleet/research/dossiers/steel.md` (Verdict section first, then Q1 to Q9). There is no claims file, so I extracted 14 load-bearing claims myself (STE-1 to STE-14). Default stance: skeptical. A claim survives only if I re-derived it by a route the author did not use.

**Method.** No browser, container lifecycle, Docker network, Hermes, keychain, sudo or git push. The only Docker commands were read-only: `docker image inspect` (image id and created time), `docker ps -a --filter name=fleet-spike` and `docker volume ls --filter name=fleet-spike`. Both listings were empty, so the dossier's "containers left running: none" holds. Routes used:

- **Raw spike outputs.** `fleet/research/spikes/steel/RESULTS.md` (every `[t1 #n]` block), the spike scripts (`lib.cjs`, `c1_flush.cjs`, `e_safe_release.cjs`, `c3_context.cjs`, `g_viewer.cjs`, `recreate.sh`, `disk_cookies.sh`), the saved screenshots, and `<scratch>/spikes/steel/*`. I re-counted sample sizes and checked what each probe actually did against what the dossier says it measured.
- **Source at the pin.** `steel-browser@1131a02` in `<scratch>/sources/steel-browser`, read independently (session service, CDP service, controller, routes, proxy util, context util, env, nginx, Dockerfile, entrypoint).
- **Chromium source at the tag shipped in the image (`152.0.7977.82`), fetched live from chromium.googlesource.com.** `sqlite_persistent_cookie_store.cc`, `sqlite_persistent_store_backend_base.cc`, `process_singleton_posix.cc`, `net/docs/proxy.md`, and all 52 CDP domain `.pdl` files (the author grepped the older `devtools-protocol` 0.0.1354347 JSON bundled in the image, not Chromium 152's own protocol).
- **Primary docs re-fetched 2026-10-10 14:52Z** (steel.dev/pricing.md, docs.steel.dev pricinglimits / profiles-api / steel-local-vs-steel-cloud, and the Terms of Service export), compared by sha256 with the corpus.
- **GitHub API (`gh`)** for repo metadata, releases, commit counts, issue and PR state, author association, review counts and tag contents.
- **Corpus OpenAPI files**, parsed to count operations.

**Spend: $0.00.** No LLM or OpenRouter calls were needed. Containers created or left running: none.

## Missed issues and errors beyond the claims

1. **The API fabricates and loses session records.** `GET /v1/sessions/{id}` returns a synthetic `released` stub for any non-active id, and `GET /v1/sessions` drops a taken-over session entirely (`resetSessionInfo` replaces the active object without archiving it). The fleet cannot detect a takeover from either endpoint; it needs its own lease and a live-argv/CDP probe (the dossier's wrapper rule 4 is right, but for a stronger reason than stated).
2. **`/v1/health` is structurally always "ok".** `isRunning()` is `this.browserInstance?.process() !== null`, which is true when there is no browser. This is a bug, not flakiness.
3. **Chromium runs as root with no sandbox, and site isolation is off.** The Dockerfile has no `USER`, so `shouldDisableSandbox` (uid 0) adds `--no-sandbox --disable-setuid-sandbox --no-zygote`, and the static args include `--disable-features=...IsolateOrigins,site-per-process...`. For a fleet that browses arbitrary social pages inside logged-in client sessions this is a security finding the dossier never mentions. It also puts renderer isolation outside what the fleet's container hardening notes cover.
4. **Injected fingerprint is internally inconsistent beyond what the dossier lists.** In the headful r1 sannysoft screenshot the page shows `navigator.userAgent` "Linux aarch64 ... Chrome/139" but `navigator.platform` "Linux x86_64". The dossier records the UA, the empty UA-CH brands and the 800x600 screen, but not this UA/platform mismatch (the default r1 run used the same aarch64 UA).
5. **Steel's own release is not graceful, and nobody explained why.** Per the puppeteer code the dossier quotes, Steel's `shutdown()` sends `Browser.close` and waits for exit, yet it leaves `Singleton*` (6/6) while a raw `Browser.close` leaves none (3/3), and a 2 s Steel release lost `localStorage` where a 2 s raw close did not. The safe-release procedure is empirical, not mechanistic. This discrepancy is not listed under "Unknowns".
6. **Upstream is slow and mostly third-party.** Both fix PRs are outside-contributor PRs with no review at all; the auth work has no maintainer owner. Steel as the "main infra" therefore means carrying its own fork for takeover guard, auth, userDataDir and fingerprint pinning, not tracking upstream.
7. **Source pin is not the tested image.** The image (2026-09-16T19:43Z) predates #366, #327 and #374, so the line numbers cited at `1131a02` may differ from the running code for anything the author did not re-check in the compiled image. (The dossier lists what it did re-check; the point is that the pin and the image are different builds.)
8. **The viewer was exercised with synthetic input only.** Special keys are sent as `keyDown` without `text`; Enter, Backspace and Tab were never tried, yet "human login" depends on them (or on clicking around them).
9. **Docs advertise an unauthenticated raw CDP port by default.** The Docker quick starts publish `-p 9223:9223`; the dossier's "never publish 9223" is correct but should be tied to that default.
10. **Unverifiable here (needs hands-on on a droplet, with Justin's yes):** metadata endpoint reachability around the proxy; `<-loopback>` through `CHROME_ARGS`; `PROXY_INTERNAL_BYPASS`; in-container argv free of proxy credentials; `FILTER_CHROME_ARGS` effect on WebGL; special-key and IME input through the viewer; native dialogs, HTTP auth, passkeys and file pickers; cross-host and x86 restore of the profile tarball; resource use on social SPAs; whether a clean-exit `Browser.close` truly skips the cookie store's `Close()`.

## Bottom line

The load-bearing findings hold: one browser per container, the 30 s cookie window and the "wait, close cleanly, then release" rule, the stale-lock silent fallback, credential echo, the unauthenticated control plane, and the Cloud pricing and ToS quotes. None of my corrections changes the fleet design. The ones most worth acting on are: remove the "`:latest` lags" and "maintainer plans auth" statements, downgrade the headful-WebGL cause, restate the stealth headline (UA-pinned is stable but host-real), add the root/no-sandbox/site-isolation finding to the risk list, and treat `/v1/sessions/{id}` and `/v1/health` as untrustworthy by construction.
