# Verification: Stagehand dossier (adversarial pass)

Date: 2026-10-10. Target: `fleet/research/dossiers/stagehand.md` and `verification/claims/stagehand.json` (SH-1 to SH-10), plus the dossier's Verdict-section claims that the fleet design depends on.

**Method.** No browsers, containers, Docker, Hermes or keychain were used. I checked each claim by a different route from the author's, using these sources:

- **Raw spike artifacts.** `<scratch>/spikes/stagehand/**`, mirrored in `fleet/research/spikes/stagehand/results/`. I re-read `llm-calls-*.jsonl`, `prompts-*.jsonl`, `result-*.json`, `run-*.stderr` and the v3 cache files, and re-counted calls myself.
- **The installed artifacts that were actually tested.** These are the npm `@browserbasehq/stagehand@4.2.0` bundle (`dist/extension/service-worker.js`), npm `3.7.3` (`dist/esm/lib/v3/**`) and the PyPI `stagehand==4.2.0` wheel.
- **Source code.**
  - `stagehand` at the pinned commit `1fc8849`. That commit is post-4.2.0 `main`: npm dist-tag `alpha` = `4.2.1-alpha-1fc8849…`. I re-checked the load-bearing logic in the 4.2.0 bundle, and it is identical.
  - `steel-browser` at `1131a02`.
- **Live fetches on 2026-10-10.**
  - Docs: docs.stagehand.dev, docs.steel.dev, and Chromium's `net/docs/proxy.md`.
  - Registry data: npm and PyPI metadata.
  - GitHub API: releases, issues, and `steel-dev` repos.
  - OpenRouter public `models` and `endpoints` listings. These are free; I made no inference calls.
- **One reproduction.** I ran a fresh-lockfile `npm audit` in `/tmp/shverify`, which writes lockfiles only and installs nothing.
- **Pure-Node regex and zod tests.** No browser was involved.

**Spend: $0.00. Containers created: none.**

1. "Steel container 666 -> 708 MiB across the probe" (RESULTS Finding 6). No raw file; it was probably read from `docker stats` and never saved.
2. "The browser (about 700 MB for this Steel container) dominates" (Q10). No raw file.
3. Python 4.2.0: "attach 43 ms", "act 480 ms", "55 MB max RSS", "0 LLM calls", and the pick "[0-207] link: Next" (Finding 8, Q1, Q2). `spike_v4_python.py` prints to stdout only, and no output file exists. The 43 ms covers `connect` plus `create`, which is about 30-50× faster than the TS figure (877-1325 ms + 414-776 ms) and is unexplained.
4. "106 MB node_modules" for v3 (Q-extra). No measurement method is recorded. `du` today gives 123 MB for `<scratch>/npm-v3/node_modules`, which includes `@ai-sdk/openai-compatible`. The "3.4 MB" figure for v4 does match npm `dist.unpackedSize` (3,571,410 bytes).
5. "~5.4k tokens" and "about 5.4k tokens" for the books.toscrape snapshot. This is `chars/4`, not a token count.
6. "String `act()` costs about 1 call and 2-5 s" (operating note 3). On loaded pages, v4 string acts took 2.5-5.0 s, and the v3 cache miss took 7.8 s. A separate data point: 5.97 s on the timed-out `/key_presses` page, where the act failed (null).
7. "`max_tokens` about 2048" and "reasoning effort low" are recommended as settings, but no alternative values were tested (largest output seen: 178 tokens). They are configuration choices, not findings.
8. "A stable release every 2-4 weeks". The npm times show gaps of up to 33 days (3.0.8 → 3.1.0) and 29 days (4.1.0 → 4.2.0).
9. Per-primitive dollar figures ($0.00013 observe, $0.00016 act, $0.00026 extract) are single samples. They depend on which OpenRouter provider served the call (missed issue 7).
10. "25.6k stars, 395 open issues". The stars are confirmed. GitHub's `open_issues_count` (395) includes open pull requests.

## Missed issues

1. **The v3 agent cache replays stale answers.**
   - `AgentCache.replayAgentCacheEntry` re-executes only the mutating steps (goto, act, fillForm, scroll, keys, navback). `extract`, `ariaTree`, `done` and `screenshot` are no-ops. It then returns `cloneForCache(entry.result)` with usage zeroed.
   - Raw `agentRun2.message` is word-for-word `agentRun1`, with usage all 0. Any read-and-report task (lead extraction, checking notifications, reading a profile) therefore returns the first run's answer with `success:true` and zero calls.
   - The cache's `configSignature` also records `openai/gpt-4.1-mini` (the v3 default), even though a custom GLM client was used.
   - This is design-changing for the dossier's "v3 as a short-lived bridge if `agent()` must exist".
2. **The positional-xpath hazard also applies to the v4 decider and observe-plan paths, not only to v3's cache.**
   - `snapshot().xpathMap` and `observe()` return positional xpaths (`/html[1]/body[1]/…/li[1]/a[1]`). `act(Action)` with `selfHeal:false` resolves the selector and acts, with no check of role, name or description.
   - The dossier's own advice to "use `observe()` once to plan multi-step flows, then `act(each)` at 0 calls" is exposed: after the first action mutates the DOM, or a feed inserts items, later planned xpaths can point at different elements. This is the same failure class as SH-8, in a shorter window.
   - The fleet's decider tier needs a re-snapshot, or a role-and-accessible-name check, before each act. Design-changing.
3. **A crashed worker can wedge the browser (from SH-6).**
   - The "one instance" lock is released only by an explicit `stagehand.close`, and the service worker is kept alive by an offscreen heartbeat.
   - The fleet needs a recovery path: relaunch the Steel session (each `POST /v1/sessions` relaunches Chromium), or send a raw `stagehand.close` JSON-RPC to the service worker before `create`.
   - Status: unverifiable (needs hands-on on a droplet).
4. **The proxy note needs correcting.**
   - A loopback CDP URL is implicitly bypassed by Chromium, and Steel sets no `--proxy-bypass-list`.
   - `PROXY_INTERNAL_BYPASS` (Steel defaults: `0.0.0.0` and `$HOST`) is needed only when the browser dials a non-loopback internal name. That is the realistic multi-container or multi-host layout.
5. **The Steel recipe has hidden launch-flag dependencies.**
   - The extension's WebSocket comes from a `chrome-extension://` origin through Steel's WebSocket proxy, so the recipe likely depends on Steel's `--remote-allow-origins=*` (`cdp.service.ts:870`).
   - `--load-extension` keeps working on Chrome 137+ only because Steel passes `--disable-features=…DisableLoadExtensionCommandLineSwitch,DisableDisableExtensionsExceptCommandLineSwitch`.
   - Headless Steel always adds the recorder extension, and that is what triggers `--disable-extensions-except`.
   - All three belong in the fleet's upgrade smoke test.
6. **The source pin and the tested artifact differ.** Line citations are to `1fc8849` on `main`, which is after 4.2.0 (the npm `alpha` tag is `4.2.1-alpha-1fc8849`). The load-bearing logic matches the 4.2.0 bundle that was tested, but future readers should cite the 4.2.0 bundle or tag. The Python wheel's extension is byte-identical to TS 4.2.0 (sha256 `98e6a987…`), which independently confirms that one baked extension serves both SDKs.
7. **Model cost and quality depend on OpenRouter routing.**
   - In the raw data, the same act on the same page cost $0.000158 on Sail Research (3,075 input tokens) and $0.000434 on Crusoe (2,756 input tokens), about 3× apart.
   - `vendor-claim` (OpenRouter API, 2026-10-10): the endpoints listing shows 38 endpoints for `z-ai/glm-5.3-flash`, priced from $0.04/M to $0.225/M input. Several are fp4-quantized (OpenInference, Sail Research, InferenceNet, Crusoe, Parasail).
   - `provider.require_parameters:true` does not pin price or quantization. The shim should set the provider order, allowed quantizations and a maximum price, and record cost per call.
8. **Q4 overstates the provider list.** The "Vertex and Azure provider options" exist in the protocol schema but can't be reached from v4 `ModelConfig`; only the 5 prefixed providers and the Browserbase gateway work.
9. **The extension has a larger footprint than described.** The v4 manifest also declares `offscreen` and an `options_page` (`wake-service-worker.html`), and runs an always-on offscreen heartbeat document. Hand this to the anti-detect and memory reviews alongside the content script.
10. **The test pages were flaky.** `the-internet.herokuapp.com/key_presses` timed out (15 s at `domcontentloaded`) in the main v4 run, and that run's variables probe failed. `RESULTS.md` reports only the successful rerun. Latency and null-rate figures from these pages are anecdotal.
11. **The 50 MiB upload path is unproven above 26 B.** The 26-byte test is the only data point. The transport for a large file is a single `Runtime.evaluate` message of tens of MB through Steel's WebSocket proxy. Status: unverifiable (needs hands-on on a droplet). The fleet should treat the in-band limit as unknown until tested, and might need the Steel files API path for much smaller videos than 50 MiB.
