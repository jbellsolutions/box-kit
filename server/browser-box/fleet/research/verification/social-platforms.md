# Verification: social-platforms dossier

Verifier: adversarial verifier (did not write the dossier). Date: 2026-10-10. Spend: $0 (OpenRouter public models list only, no chat call).
No browser, container, hermes CLI, HOME override, `gh`, sudo or keyring was used. Only `curl`/`python3 -I` HTTP GETs to public pages and the WebFetch/WebSearch tools.
Dossier: `fleet/research/dossiers/social-platforms.md`. Claims file: `fleet/research/verification/claims/social-platforms.json`.

## Method and how it differs from the author

- The author rendered Meta/TikTok docs with a natively launched Chromium (see "Missed issues", item 1). I did not render. I re-fetched by other routes:
  - X: `docs.x.com/*.md` (curl) plus the 2025-06-17 Wayback snapshot of the same rate-limit page for history, and `openapi.json` for auth schemes.
  - Facebook/Instagram/TikTok ToS and Community Standards: raw files at the pinned Open Terms Archive commits (`raw.githubusercontent.com/OpenTermsArchive/pga-versions/<sha>/...`), not the author's copies.
  - Facebook ToS: Wayback `20261010002416id_`. LinkedIn help: Wayback `20261002024940id_`. X automation: Wayback `20261001071835id_` (dateModified 2026-09-28). X limits: Wayback `20260926193021id_`. X locked/limited: Wayback `20260921142432id_`.
  - LinkedIn: `learn.microsoft.com` pages by curl.
  - TikTok Business API docs: the public doc-node JSON endpoint (same endpoint the author used; the page content is the primary source). TikTok developer pages and Meta developer docs: WebFetch tool, 2026-10-10.
- WebFetch output is a small-model extract of the page, not verbatim text. Items that rest only on WebFetch are marked `[webfetch]`. Where WebFetch dropped something the author's own render contained (the IG 7-day human_agent window, line 102 of the saved page), I used the author's saved render as a cross-check and said so.
- Spike (SP-12): re-ran the committed script by plain HTTP against public test pages (stdlib urllib, no browser) and read the raw `run1-3.jsonl`.

## Unsourced numbers

Numbers in the dossier with no source or measurement behind them (or only an assumption):

- "Never exceed 50% of any per-account cap" / "run at <= 50% of caps" (Q3 item 5, governor row, recommendations). A policy choice with no basis given.
- "One read-only login-state probe per account per week" (keep-warm). No source; see V-12.
- "1,000 accounts x 3 link posts a day = about $600/day". Arithmetic is right; the 3 posts/day workload is invented.
- "LinkedIn ~100 invitations/week". Third-party folklore (labelled as such in the dossier); no LinkedIn source.
- "~$0.001 per call on GLM 5.3 Flash". Estimate from an assumed 8k-token prompt (scale-infra.md `[estimate]`), not measured on social DOMs.
- "Meta Ad Library blocked after 2-3 searches; Instagram rate-limited after ~24 scrolls". Present in an older local tool's anti-detection results (private; details withheld) but an old logged-out test, not reproduced, and unrelated to logged-in client sessions.
- "Tier 0 handled static pages ... most of the contact data lives in static HTML" (RESULTS.md finding 1). Not measured: every live test page returned empty JSON-LD, mailto, tel and social lists. The only populated result is a fixture the author wrote.
- "70-344 ms per page": real, but 12 single fetches from one Mac to five public test hosts. Not a distribution, not company websites.
- TikTok "40 QPM / 600-1,000 QPM per app" and X 2,400 legacy figure are sourced; the "15 posts/day" for the Content Posting API is "typically", per the author's saved guidelines copy (line 62), and the live direct-post reference page has no such figure.

## Missed issues

1. **The author's evidence collection broke the BRIEF.** `<scratch>/spikes/social-platforms/render/render.cjs` calls `chromium.launch({executablePath: <a local Chrome for Testing binary>, headless: true})`, a native browser launch on the maintainer's Mac. BRIEF.md bans exactly this (native Playwright `launch()`), while the dossier header says "Containers started: none". It was not necessary: the same Meta and TikTok developer pages returned through plain fetch tooling in this verification. Record it as a process violation; do not reuse the script.
2. **X "Automated account" rules are explicit** (V-8): label, bio disclosure, human-managed account link, opt-out. The dossier files this as unverified risk 5; the rule text exists and shapes whether client brands will accept the product.
3. **The X 10,000-posts and 1,440-DMs ceilings are legacy Pro-tier values** (SP-3). Whether they bind a pay-per-use app, and whether they aggregate user-token writes, is unproven. The "Enterprise needed at 1,000 accounts" conclusion rests on it.
4. **X account-level caps are tighter than the governor's** (V-2): 50 original posts + 200 replies per day for unverified accounts, 500 DMs/day.
5. **X competitive analysis is prohibited**: the developer guidelines list "App benchmarks X performance vs competitors | Prohibited competitive analysis". Any client benchmarking offering on X analytics is out. The dossier's lead-gen section only covers profiling.
6. **Consent-based lead channels are missing** (SP-11): Lead Ads, DM opt-in capture, LinkedIn Lead Gen Forms, TikTok instant forms are official, sanctioned lead sources. The dossier's "open web only" for leads is incomplete for client-run campaigns.
7. **Messenger One-Time Notification, Sponsored Messages and LinkedIn Sponsored Messaging** are outbound-after-contact or paid channels not covered under "messaging" (SP-10).
8. **Messenger bots must answer within 30 s** is listed but not carried into the design. A reasoning-model reply path on slow turns would reclassify the bot or break the rule.
9. **Meta system-user caveat**: system user tokens "represent servers or software making API calls to assets owned or managed by a Business Manager" and must not be used to act "on behalf of a real user of your software" unless taken through Facebook Login. The dossier recommends both "OAuth per client to one app" and "system user" without noting that these are two different onboarding models (Business Manager partner access vs. client OAuth).
10. **TikTok Content Posting audit also requires "a wide audience, not limited to internal groups/private use"** (SP-6). An agency-internal fleet may fail the same test in Accounts API review. Approval odds are unknown (the dossier says so) but this criterion should be named.
11. **Doc-internal conflicts the dossier did not record**: IG messaging send rate (300/s vs 100/s on one page); IG publishing 100 vs 50 (recorded); LinkedIn member analytics (closed permission vs approved use case text).
12. **Hands-on is entirely absent for platform behaviour.** Every checkpoint, cadence and account-health statement is document analysis. That is honest in the dossier, but the lead-gen cascade is the only measured item and it rests on five sandbox pages (SP-12). Unverifiable (needs hands-on on a droplet): live X header semantics, Meta App Review/Advanced Access feasibility for an agency, TikTok Accounts API acceptance for an agency-internal fleet, whether API activity resets Meta's dormancy clock.

## Bottom line

The load-bearing policy conclusions survive: X browser automation is banned (SP-1), TikTok's Content Posting audit rejects internal upload tools (SP-6), Facebook Groups has no API (SP-7), LinkedIn messaging needs a human action per message (SP-8), and no platform allows cold DMs (SP-10). What needs correcting before the fleet design relies on the dossier: the X per-app ceilings and their scope (SP-3), the "prolonged dormancy" trigger (SP-9, which removes the rationale for a weekly Meta login probe), the label requirement for X automated accounts (V-8), and the strength of the SP-12 spike conclusion.
